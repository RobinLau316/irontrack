## 1. 执行原则

- 分成“动作库整理”和“程序接入”两个阶段。
- 阶段一完成后必须由用户审核分类结果；未通过前不进入阶段二。
- 不把上游 1,324 条原始数据或媒体直接放入正式网页。
- 不修改、删除或提交用户现有的未跟踪文件 `src/app/(app)/training/page 2.tsx`。
- 不在正式运行时请求 GitHub、Gym visual 或其他动作资源。
- 发布前要求用户从“我的 → 本地备份”导出一次现有数据。
- 所有兼容处理先生成恢复快照，只补充字段，不覆盖旧训练内容。

## 2. 计划产物

计划严格按以下文件边界新增或更新内容；如实施时发现现有结构无法支持，必须先修改本计划并重新确认，不能临时混合职责。

### 数据整理工具

- `tools/exercise-catalog/source-lock.json`：记录仓库、固定提交、源文件校验值和许可边界。
- `tools/exercise-catalog/equipment-map.json`：上游 28 类器械到 IronTrack 中文器械枚举的映射。
- `tools/exercise-catalog/muscle-map.json`：上游目标肌群到 IronTrack 标准肌群的映射。
- `tools/exercise-catalog/curation-overrides.json`：中文名称、别名、PPL、动作模式、替代组、审核状态和排除原因。
- `scripts/import-exercise-source.mjs`：只在整理阶段读取固定上游数据并验证来源。
- `scripts/build-exercise-catalog.mjs`：生成候选报告和正式本地动作库。

### 正式运行资源

- `public/data/exercise-catalog.v1.json`：精简目录，不包含长说明和媒体路径。
- `public/data/exercise-instructions-zh.v1.json`：按稳定编号保存经校对的中文步骤，按需加载。
- `public/exercise-engine.js`：独立的本地筛选、排序、轮换、结构校验和旧名称映射逻辑。
- `THIRD_PARTY_NOTICES.md`：记录数据来源、固定版本、MIT许可和媒体未使用声明。
- `index.html`：只负责调用动作引擎、保存兼容数据和渲染已确认的新增交互。

### 审核与测试

- `docs/superpowers/reviews/2026-09-02-exercise-catalog-review.md`：推、拉、腿、肌群和器械分类审核报告。
- `scripts/check-exercise-catalog.mjs`：动作库结构、数量、重复、许可和性能预算检查。
- `scripts/check-exercise-engine.mjs`：候选过滤、轮换比例、反馈、结构平衡和回退场景测试。
- `scripts/fixtures/exercise-engine-scenarios.json`：不含个人真实数据的测试场景。
- `scripts/check-static.mjs`：继续检查现有功能，并增加正式资源引用和媒体禁用标记。
- `package.json`：让 `npm run check` 依次执行静态、动作库和动作引擎检查。

## 3. 阶段一：动作库整理

### 任务 1：固定数据源与许可边界

1. 记录上游仓库、提交哈希、`exercises.json` 校验值和导入日期。
2. 验证源数据为 1,324 条、编号唯一、必要字段和十种语言说明完整。
3. 在导入工具中明确排除 `image`、`gif_url` 和媒体文件复制。
4. 生成第三方许可说明，区分 MIT 数据/文字与未获授权媒体。

验收：更换提交、源文件校验失败、记录数量异常或字段缺失时，导入必须停止并报告原因。

### 任务 2：标准化器械、肌群和旧动作

1. 建立上游 28 类器械到现有中文器械选项的明确映射。
2. 建立标准主要肌群、辅助肌群和单一 `replacementMuscle`。
3. 为肩、肘腕、腰背、髋、膝、踝建立保守 `loadRegions` 标签；该标签只用于过滤，不代表医学判断。
4. 为当前 91 个不重复中文动作建立稳定编号和别名映射。
5. 对无法唯一对应上游动作的现有动作分配 IronTrack 自有编号，不强行匹配。

验收：任何正式动作都不能出现未映射器械、空主要肌群、多个替换匹配肌群或歧义旧名称映射。

### 任务 3：筛选与中文校对

1. 优先筛选胸、肩、三头、背、二头、腿、臀、核心相关动作。
2. 去除纯拍摄视角重复、同名重复、冷门器械和当前无法解释的动作。
3. 补充常见中文健身名称、中文别名、PPL标签、动作模式、替代组和结构标签。
4. 将动作分为“允许自动推荐、仅手动、暂停发布、排除”；本阶段正式目录只发布允许自动推荐和保留兼容所需动作。
5. 校对准备上线动作的中文步骤，修正器械术语和生硬翻译。
6. 正式动作总量控制在约 200～300 个；不为达到数量强行纳入低质量动作。

验收：正式动作编号和中文名称唯一，字段完整，不含媒体路径，不含未审核说明。

### 任务 4：生成用户审核报告

报告至少包含：

- 推、拉、腿动作数量。
- 胸、肩、三头、背、二头、股四、腘绳、臀、小腿和核心覆盖数量。
- 徒手、哑铃、杠铃、绳索、史密斯和常见固定器械覆盖数量。
- 当前 91 个动作的保留、合并和自有编号情况。
- 因重复、器械、术语、动作质量或范围原因排除的数量。
- 少量需要用户判断的边界动作。

### 停顿点 A：用户审核动作分类

完成阶段一后停止。用户只需要审核分类覆盖、数量和边界动作，不需要阅读代码或逐条审核全部动作。只有用户回复“动作库分类通过”后，才能进入阶段二。

## 4. 阶段二：程序接入

### 任务 5：加入可测试的动作引擎

将筛选和轮换逻辑从页面渲染中分离，形成纯数据输入输出的本地引擎：

- `normalizeExercise`：校验和标准化动作。
- `resolveLegacyExercise`：按稳定编号、中文名称和别名唯一映射旧动作。
- `filterCandidates`：执行审核状态、PPL、肌群、器械、不适、暂停推荐和避开动作过滤。
- `selectRotationSlots`：根据辅助动作数量选择约 30%～40% 的替换槽位。
- `scoreCandidates`：优先选择最近两次同类训练未使用、最久未出现且变式合适的动作。
- `validatePlanBalance`：校验推、拉、腿最低结构覆盖。
- `buildFallbackPlan`：动作库或 AI 异常时继续使用当前内置动作。

同一用户、同一周期和同一动作库版本必须得到稳定候选顺序，避免刷新或重复渲染随机改变计划。

### 任务 6：接入目录加载与回退

1. 只有进入训练设置或生成计划时才加载精简目录。
2. 中文步骤只在用户展开新动作说明时加载一次并缓存。
3. 目录加载、JSON解析、版本或字段校验失败时，明确回退当前内置动作库。
4. 回退不得清除今日设置、已生成计划或进行中训练。

性能预算：

- 精简目录目标不超过 250KB 未压缩。
- 中文步骤目标不超过 300KB 未压缩，且不进入首页首屏请求。
- 不增加任何上游媒体或运行时外部请求。

### 任务 7：数据兼容与备份升级

1. 新计划和训练记录增加 `exerciseId`、名称快照和动作库版本。
2. 新增 `exercise_preferences`，保存暂停推荐和“继续进阶/换变式”选择。
3. 登录或导入旧备份后执行唯一映射；成功时只补充 `exerciseId`，保留原名称和全部组记录。
4. 映射歧义或失败时不修改该记录。
5. 升级前保存一次兼容恢复快照。
6. 普通备份版本升级，并纳入动作库版本和动作偏好；API Key继续排除。

验收：旧数据导入、升级失败和重复执行迁移都不能产生重复记录或覆盖历史重量、次数、反馈和时间。

### 任务 8：改造计划生成和 AI 校验

1. 保留核心动作 4～6 周和锁定规则。
2. A/B继续作为轮换阶段，不再使用永久固定完整清单。
3. 每次只选择约 30%～40% 的辅助动作槽位进行替换。
4. 替换动作 `replacementMuscle` 必须与原槽位一致。
5. 用本地结构校验保证：
   - 推日保留水平推、垂直推或肩部刺激、肘伸。
   - 拉日保留水平拉、垂直拉、肘屈或后束刺激。
   - 腿日保留膝主导、髋主导、屈膝或单腿刺激、小腿和核心覆盖。
6. AI提示词只包含合格动作编号和必要字段；返回结果必须使用稳定编号。
7. AI越界、重复、器械不符、暂停推荐或结构失衡时拒绝并回退本地候选。

离散动作数量下，替换槽位按最接近 35% 的整数计算，至少替换 1 个且至少保留 1 个辅助动作；验收允许因整数取整产生小幅比例偏差。

### 任务 9：接入反馈和用户控制

1. “不适”反馈完成后，将动作编号加入暂停推荐列表。
2. “吃力”只进入训练量调整，不触发自动替换。
3. 上次“轻松”的辅助动作在预览中默认“继续进阶”，并提供“换个变式”。
4. “换个变式”只替换当前动作，重新执行候选和结构校验。
5. “我的”增加暂停推荐管理；手动恢复后动作才能重新参与候选。

### 任务 10：接入新动作说明

1. 用户历史中不存在稳定编号或唯一别名匹配时，动作标记为“新动作”。
2. 计划预览和正式训练均提供默认收起的中文步骤。
3. 动作完成前保持“新动作”状态；仅生成或预览不视为已经练过。
4. 步骤加载失败时隐藏说明并保留训练操作。
5. 展开说明不得影响计时、休息、输入焦点、固定操作区或刷新恢复。

## 5. 自动检查与场景验收

### 5.1 数据检查

- 正式动作数量处于约 200～300 个。
- 稳定编号、中文名称和来源映射无冲突。
- 自动推荐动作字段完整，中文步骤已审核。
- 不存在 `image`、`gif_url` 或媒体文件引用。
- 精简目录和说明文件满足性能预算。

### 5.2 引擎场景

至少覆盖：

- 推、拉、腿在 30、45、60、90 分钟下生成 8、10、12、15 个动作。
- 核心动作保持和锁定。
- 辅助动作只替换约 30%～40%。
- 替换候选避开最近两次同类训练记录。
- 单个动作跨模式后主要肌群一致且整套结构合格。
- 健身房、家用哑铃和家用徒手器械过滤。
- 当天不适、用户避开和暂停推荐过滤。
- “吃力”“轻松”“不适”三种反馈规则。
- 候选不足、目录损坏、AI越界和无API回退。
- 同一输入重复运行结果稳定。

### 5.3 数据兼容

- 当前格式、缺失字段、旧备份和进行中训练分别测试。
- 唯一名称正确映射，歧义名称保持原样。
- 兼容迁移可重复执行且不产生二次修改。
- 导出再导入后动作偏好、历史和进行中训练一致。

### 5.4 手机回归

- 320×568、375×667、390×844 下无横向溢出。
- 计划预览的新动作标签、说明和选择按钮完整显示。
- 训练页说明展开后固定操作区和底部导航不遮挡。
- 首页不提前加载动作说明文件。
- 原有生成、预览、替换、训练、休息、反馈、完成、统计和恢复闭环通过。

## 6. 提交、发布与线上核验

建议按可回退边界分为以下提交：

1. 数据源锁定、导入和校验工具。
2. 精选动作目录、中文步骤和审核报告。
3. 动作引擎及自动测试。
4. 数据兼容、备份和计划生成接入。
5. 页面交互、回归测试和文档状态更新。

阶段一分类审核和阶段二完整验收均通过后，才推送 `main` 触发 GitHub Pages 发布。线上核验包括：

- 动作目录和中文步骤文件可访问。
- 首页首屏没有外部动作资源请求。
- 无API仍可生成计划。
- 新动作说明、部分轮换和暂停推荐功能可用。
- 已有训练历史和进行中训练仍能读取。
