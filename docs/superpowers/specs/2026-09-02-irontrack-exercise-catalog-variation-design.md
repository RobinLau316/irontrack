# IronTrack 精选动作库与智能变式设计规格

日期：2026-09-02
状态：规格已确认；阶段一已通过分类验收；阶段二已完成本地实现和主要回归，待发布前用户备份及线上验收
对应 PRD：`docs/superpowers/specs/2026-08-28-irontrack-prd.md` 第 15 章
数据来源：`hasaneyldrm/exercises-dataset`，审计版本 `7455efae41b330c265e7cd4b78dfa848e7ce5ebd`

## 1. 背景与目标

当前 IronTrack 已具备 PPL 循环、核心动作锁定、辅助动作 A/B 轮换、历史反馈、器械和不适过滤、本地备用计划及 AI 边界校验。现有正式动作库共 102 条配置、91 个不重复中文动作，能够完成基础训练闭环，但辅助动作候选数量和替代关系有限，同类训练经过若干轮后容易再次出现相似组合。

本设计利用 `hasaneyldrm/exercises-dataset` 的动作名称、身体部位、目标肌群、辅助肌群、器械和多语言说明，建立适合 IronTrack 的精选本地动作库。首要目标是让辅助动作出现有依据、可控制的变化，同时保持核心动作稳定、训练结构完整、历史数据连续和离线可用。

## 2. 数据源审计结论

审计版本包含 1,324 条记录、28 类器械和 10 种语言说明。记录具有稳定的原始编号、英文名称、身体部位、主要及辅助肌群、器械、中文步骤和媒体路径。

数据源不能直接作为 IronTrack 推荐引擎，原因包括：

- 1,324 条记录中包含不同拍摄视角、细微变体、重复名称、冷门器械和不适合当前 PPL 目标的动作。
- 动作名称只有英文；中文说明虽然字段完整，但部分术语和表达需要人工校对。
- 数据源不包含 IronTrack 所需的 PPL 归属、动作模式、核心/辅助适用性、替代关系、推荐等级、训练量默认值和不适过滤标签。
- 原始 JSON 约 17.4MB，不适合在当前手机静态页面中整库加载。
- 代码、数据结构和说明文字采用 MIT 许可；`images/` 与 `videos/` 中的媒体不受 MIT 许可覆盖，不能直接用于 IronTrack。

## 3. 范围

### 3.1 本阶段包含

- 从全部记录中精选约 200～300 个适合 PPL 力量训练及当前器械环境的动作。
- 建立中文名称、英文名称、别名、PPL 归属、肌群、动作模式、器械、替代组、推荐等级和中文步骤。
- 为现有动作和新动作建立稳定编号。
- 优化辅助动作部分轮换、近期重复控制、反馈适配和 AI 候选约束。
- 在计划预览和训练页面为新动作提供可展开中文步骤。
- 增加暂停推荐动作的恢复管理。
- 兼容现有历史、进行中训练和备份。

### 3.2 本阶段不包含

- 不导入或发布数据源的图片与 GIF。
- 不建立完整动作浏览、搜索、收藏或自由编排页面。
- 不增加后台服务器、云数据库或运行时 GitHub 请求。
- 不扩展为康复处方、伤病判断或医疗建议。
- 不改变 PPL 周期、单次 8～15 个动作和核心动作 4～6 周稳定规则。
- 不实施跨设备同步或自动跟随上游更新。

## 4. 总体结构

采用“固定上游版本、构建时精选、运行时本地使用”的结构。

1. 导入工具读取固定提交版本的数据文件。
2. 转换层统一器械、肌群和名称，并排除不合格记录。
3. 人工审核层确认中文名称、中文步骤、PPL 归属、动作模式、替代关系和自动推荐资格。
4. 生成两类本地发布资源：
   - 精简目录：随计划功能加载，包含筛选和排序所需字段。
   - 中文步骤：只有查看新动作说明时按需加载。
5. IronTrack 本地规则从精简目录筛选和排序候选。
6. AI只能从规则给出的合格候选中选择并说明理由。

正式运行不依赖上游仓库、第三方接口或后台服务。后续升级数据源时必须固定新版本，重新运行校验并人工复核，不能自动覆盖当前动作库。

## 5. 动作数据模型

每个精选动作至少包含以下字段：

| 字段 | 用途 |
|---|---|
| `exerciseId` | IronTrack 稳定编号；数据源动作使用带来源前缀的编号 |
| `sourceId` | 上游原始编号，便于追溯 |
| `nameZh` | 界面使用的常见中文健身名称 |
| `nameEn` | 上游英文名称 |
| `aliasesZh` | 旧名称、常用别名及历史映射名称 |
| `pplTags` | 可用于推、拉、腿中的一个或多个训练日 |
| `primaryMuscles` | 主要训练肌群，可为多个标准肌群标签 |
| `replacementMuscle` | 用于自动替换匹配的单一标准主要肌群 |
| `secondaryMuscles` | 辅助肌群 |
| `movementPatterns` | 水平推、垂直推、水平拉、垂直拉、膝主导、髋主导等 |
| `equipment` | 映射为 IronTrack 现有中文器械枚举 |
| `loadRegions` | 肩、肘腕、腰背、髋、膝、踝等保守过滤标签，不代表医学判断 |
| `roleEligibility` | 是否允许作为核心动作、辅助动作或仅手动使用 |
| `variantGroup` | 同一动作家族或技术变式分组 |
| `substitutionGroup` | 主要肌群相同、可以参与候选替换的分组 |
| `balanceTags` | 用于检查整套计划结构是否完整 |
| `recommendationStatus` | 自动推荐、仅手动、暂停发布或排除 |
| `qualityTier` | 审核等级，自动推荐只使用合格等级 |
| `instructionZh` | 经术语校对的分步骤中文说明 |
| `trainingDefaults` | 没有历史记录时使用的默认组数、次数和休息时间；有历史后由渐进规则接管 |
| `catalogVersion` | 动作库版本 |

数据源不提供的 PPL、动作模式、替代关系和训练结构字段必须由 IronTrack 转换规则和人工审核补齐，不能让 AI 临时推断后直接写入正式动作库。

## 6. 精选与审核规则

### 6.1 纳入范围

- 服务胸、肩、三头、背、二头、腿、臀和核心等 PPL 训练目标。
- 优先覆盖现有器械设置，以及徒手、哑铃、杠铃、绳索和常见固定器械。
- 动作名称、目标肌群和执行步骤能够明确解释。
- 能够归入清楚的替代组和计划结构标签。

### 6.2 排除或降级

- 只因拍摄视角不同而产生的重复记录只保留一个动作概念。
- 冷门且当前器械设置无法表达的动作不进入自动推荐池。
- 中文术语、目标肌群或执行方法无法可靠确认的动作暂停发布。
- 需要超出普通健身场景专业监督的动作不自动推荐。
- 数据源分类与 IronTrack 审核结果冲突时，以人工审核后的正式字段为准，并保留来源字段供追溯。

### 6.3 用户审核方式

动作先按推、拉、腿、主要肌群和器械生成分类清单。用户审核分类数量、覆盖范围和少量边界动作，不要求逐条审核全部动作。只有通过分类审核的动作才能进入自动推荐池。

## 7. 计划变化与替换规则

### 7.1 核心动作

- 每个训练日保留 1～2 个核心动作。
- 核心动作默认稳定 4～6 周。
- 只有用户反馈“不适”、器械不可用、用户主动解除锁定或既有 PRD 允许的条件才提前建议替换。
- AI不得自行更换锁定核心动作。

### 7.2 辅助动作部分轮换

- 保留现有 A/B 周期状态和界面标识，作为辅助动作轮换阶段；A/B 不再代表两份永久固定的完整动作清单。
- 每次同类训练只替换约 30%～40% 的辅助动作，保留约 60%～70%。
- 需要替换的槽位优先从最近两次同类训练没有使用过的动作中选择。
- 单个动作可以跨动作模式替换，但 `replacementMuscle` 必须一致。
- 最终整套计划必须通过结构平衡检查，不能因为跨模式替换而丢失必要的推、拉、膝主导、髋主导或其他计划结构。
- 候选不足时，优先复用最久未出现的合格动作，不放宽器械、不适、暂停推荐或用户避开规则。

### 7.3 候选筛选顺序

硬性过滤依次检查：

1. 动作已通过审核并允许自动推荐。
2. 适用于当前 PPL 训练日和目标肌群。
3. 符合当前训练环境和用户器械。
4. 不在用户避开动作、暂停推荐或不适过滤范围内。
5. 加入后整套计划仍能满足结构平衡。

通过硬性过滤后，再按近期重复、历史反馈、当前动作覆盖、变式关系和最久未使用时间排序。AI只能接收排序后的合格候选，不得扩大候选范围。

结构平衡由本地配置校验：推日至少保留水平推、垂直推或肩部刺激、肘伸；拉日至少保留水平拉、垂直拉、肘屈或后束刺激；腿日至少保留膝主导、髋主导、屈膝或单腿刺激，并保留小腿和核心覆盖。核心动作已经满足的结构可以计入最低要求。

### 7.4 反馈规则

- “不适”：动作立即加入暂停推荐列表，只有用户手动恢复后才能重新进入候选池。
- “吃力”：只调整重量、次数或组数，不因连续“吃力”自动替换。
- “轻松”：下次同类计划预览中显示“继续进阶 / 换个变式”；默认选择继续进阶，用户可切换为同肌群变式。
- “合适”：按正常部分轮换和渐进规则处理。

## 8. 页面与交互

### 8.1 计划预览

- 显示中文动作名、主要肌群、核心/辅助标识和选择理由。
- 首次进入用户计划的动作显示“新动作”标签。
- 新动作提供默认收起的中文步骤。
- 上次反馈为“轻松”的辅助动作显示“继续进阶 / 换个变式”。
- 替换只作用于当前动作，不改变其他动作或锁定核心动作。

### 8.2 正式训练

- 新动作保留“查看动作说明”入口。
- 展开后显示简短、分步骤中文说明。
- 展开说明不得中断计时、完成记录、休息状态或刷新恢复。

### 8.3 我的

- 增加“暂停推荐的动作”管理区。
- 显示因“不适”暂停的动作及暂停原因。
- 只有用户主动点击“恢复推荐”后，动作才重新参与计划。

本阶段不新增完整动作库页面。新增控件沿用“午夜竞技”视觉系统，并继续满足 44px 触控面积、底部安全区和窄屏完整显示要求。

“新动作”指该用户历史记录中不存在相同稳定编号，且旧名称或别名也没有唯一匹配记录的动作。动作未真正完成前，即使重新生成计划仍保持“新动作”状态。

## 9. 数据兼容与备份

- 新计划和新训练记录同时保存稳定动作编号及当时显示的中文名称。
- 旧记录通过中文名称和别名关联动作编号，原名称始终保留。
- 只有唯一匹配时才自动关联；歧义和无法识别的旧记录保持不变。
- 数据兼容处理只补充字段，不删除或覆盖组记录、重量、次数、反馈和时间。
- 执行兼容升级前生成一次恢复快照。
- 普通备份增加动作库版本、暂停推荐列表和动作选择偏好；API Key仍不进入备份。
- 导入旧备份后重新执行非破坏式映射，不要求旧备份已经包含动作编号。

## 10. 异常回退

- 精选动作库加载或校验失败：使用当前内置动作库生成计划，并明确显示回退状态。
- 中文步骤缺失：隐藏说明入口，不阻断计划和训练。
- 候选不足：复用最久未使用的合格动作；仍不足时使用当前内置动作库对应动作。
- AI返回动作库之外、已暂停或器械不匹配的动作：拒绝结果并使用本地候选或本地计划。
- 历史映射存在多个候选：不自动写入动作编号。
- 动作库版本与备份版本不一致：保留记录中的名称快照，并按别名映射；无法映射时原样显示。

## 11. 授权与内容质量

- 项目中记录数据源仓库、固定提交、MIT许可和必要版权声明。
- 不复制、部署或运行时加载数据源的图片与 GIF。
- 中文名称和说明上线前必须完成健身术语校对。
- 数据集说明不能作为伤病诊断、安全保证或康复处方。
- 上游更新必须作为新版本重新审核，不自动同步。

## 12. 实施阶段

### 阶段一：动作库整理与分类验收

1. 固定数据源版本并建立导入校验。
2. 去重、器械映射和PPL初筛。
3. 补充中文名称、别名、动作模式、替代组和推荐等级。
4. 校对准备上线的中文步骤。
5. 输出推、拉、腿及器械分类审核清单。
6. 用户确认分类结果和边界动作。

### 阶段二：程序接入与发布

1. 接入精简目录和按需中文步骤。
2. 增加稳定编号、历史映射和备份兼容。
3. 改造本地候选评分与辅助动作部分轮换。
4. 限制 AI 候选范围。
5. 增加新动作说明、轻松反馈选择和暂停推荐管理。
6. 完成功能、数据、性能和线上验收后发布。

阶段一审核未通过前，不进入阶段二。

## 13. 验收标准

1. 精选动作数量处于约 200～300 个，全部具有稳定编号、常见中文名称、PPL归属、肌群、器械、推荐状态和审核结果。
2. 现有用户、计划、历史、反馈和进行中训练完整保留；歧义记录不被错误映射。
3. 单次计划仍按时间生成 8～15 个正式动作。
4. 正常情况下核心动作稳定 4～6 周。
5. 同类训练每次只轮换约 30%～40% 的辅助动作。
6. 新替换动作优先避开最近两次同类训练使用过的动作。
7. 单个替换保持主要肌群一致，最终计划通过结构平衡检查。
8. 器械、不适、用户避开和暂停推荐动作不会进入最终计划。
9. “吃力”不自动换动作；“轻松”可在预览中选择继续进阶或换变式。
10. 新动作在计划预览和正式训练中均可查看中文步骤。
11. 无 API、AI结果异常、动作库加载失败或旧备份导入时，核心训练闭环仍可用。
12. 手机首屏不加载完整上游数据或未授权媒体；现有加载速度、固定底栏和训练操作不得退化。
13. 正式运行不访问 GitHub 或 Gym visual，不依赖外部动作资源。

## 14. 成功定义

连续完成多个 PPL 循环后，核心动作保持可追踪的稳定性，辅助动作每轮产生约 30%～40% 的可解释变化；新动作来源、训练目标和使用理由清楚，用户仍能在计划预览中控制是否采用。实现不得以牺牲历史数据、离线备用计划、器械匹配或训练现场操作效率为代价。
