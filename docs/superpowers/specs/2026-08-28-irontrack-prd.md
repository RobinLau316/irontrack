# IronTrack 个人 AI 训练助手 PRD

版本：V1.1
日期：2026-09-02
状态：核心功能 P0、P1 与 V1.1 UI 视觉改版已上线；第 15 章仅完成阶段一动作库整理，尚未接入或发布

## 1. 文档目的

本 PRD 从现有 IronTrack 网页反向梳理产品需求，明确产品定位、训练计划生成规则、核心功能、数据边界和验收标准。本文描述目标产品，不代表当前网页已经具备全部能力。

## 2. 产品定义

### 2.1 产品名称

IronTrack 个人 AI 训练助手。

### 2.2 目标用户

以产品所有者本人为核心用户：有一定力量训练经验，采用 PPL 训练分化，希望减少每天编排训练计划的精力，同时保留渐进训练、动作变化和个人控制权。

当前版本按单机、单人主场景设计。现有本地用户切换能力可以保留兼容，但不作为首期重点，也不扩展教练端或多人协作能力。

### 2.3 核心问题

训练前需要自行判断今天练什么、安排哪些动作，并结合身体状态、训练时间和现场器械做调整，决策成本较高。

### 2.4 核心价值

用户打开手机网页后，系统根据 PPL 周期、训练历史和当天状态生成可执行计划，使用户在正常情况下约 2 分钟内开始训练，无需另外查动作或自行编排。

### 2.5 产品原则

1. 程序规则决定训练骨架和边界，AI 负责结合当天状态做适配和解释。
2. 核心动作保持稳定，辅助动作按 A/B 方案轮换。
3. AI 只提出动作、训练量和渐进负荷建议，最终由用户确认。
4. AI 不可用时，本地规则仍能生成可训练计划。
5. 训练开始后不再依赖 AI，网络异常不能中断执行和记录。
6. 数据默认保存在本机，并提供导出备份和导入恢复。

### 2.6 首期非目标

- 健身知识内容库的持续建设。
- 面向大众用户的注册、订阅和运营体系。
- 教练端、学员端和多人协作。
- 云端同步和跨设备自动同步。
- 医疗、康复或伤病诊断。
- 原生 iOS 或 Android 应用。

## 3. 核心使用流程

1. 系统根据已完成训练推荐今天的 PPL 训练日。
2. 用户可接受推荐，也可临时调整训练部位。
3. 用户填写身体状态、可用时间、训练环境、不适部位和避开动作。
4. 本地规则生成计划骨架，AI 在规则范围内完成适配。
5. 用户预览计划，锁定、替换或修改动作后确认。
6. 用户开始训练，逐组记录实际重量和次数。
7. 每个动作结束时选择“轻松、合适、吃力、不适”。
8. 训练完成后保存记录，更新 PPL 周期、核心动作阶段和下次渐进建议。

## 4. 信息架构与首期范围

### 4.1 今日首页

- 显示推荐训练日及推荐原因。
- 显示当前 PPL 周期进度。
- 显示上次训练摘要和本周完成情况。
- 提供“生成今日计划”主入口。

### 4.2 训练体系

- 展示当前 PPL 分化结构。
- 展示各训练日的核心动作及 A/B 辅助动作。
- 显示当前训练阶段及核心动作连续使用时间。
- 支持锁定和解除锁定核心动作。
- 展示动作替换与渐进负荷原则。

### 4.3 训练执行

- 完成生成前设置、计划预览、训练记录、休息计时、动作反馈和训练总结。
- 已确认计划和训练进度必须保存在本机，刷新后可以继续。

### 4.4 数据复盘

- 查看历次训练记录。
- 查看核心动作重量和次数趋势。
- 查看每周训练次数、总组数、总容量和训练时长。
- 查看动作反馈变化和系统调整依据。

### 4.5 个人设置

- 管理身体数据、目标、经验、器械和训练模板。
- 管理 DeepSeek API Key。
- 导出备份、导入恢复。

## 5. 训练计划生成规则

### 5.1 PPL 周期推荐

- 系统按实际完成记录推进“推 → 拉 → 腿 → 推”的循环。
- 用户临时改练其他部位时，以实际完成的训练更新下一次推荐。
- 未完成的训练计划不计入周期进度。
- 首次使用时默认从推日开始，用户可以修改。

### 5.2 单次计划结构

每次训练由以下内容组成：

1. 动态热身。
2. 1～2 个核心动作。
3. 辅助动作。
4. 拉伸放松。
5. 简短饮食建议。

正式训练动作总数根据可用时间调整，必须处于 8～15 个范围内。时间较短时靠近下限，时间较长时靠近上限；规则引擎同时校验预计总时长，避免动作数量与可用时间明显冲突。

### 5.3 核心动作

- 每个训练日设置 1～2 个核心动作。
- 核心动作默认连续保留 4～6 周，便于比较重量、次数和完成质量。
- 核心动作持续进步时继续保留。
- 出现以下任一情况时可以提前建议替换：
  - 连续 3 次同类训练未达到既定目标，且不是因为临时缩短训练时间。
  - 用户反馈“不适”。
  - 当天器械不可用。
  - 用户主动解除锁定并要求替换。
- AI 不得在没有说明原因的情况下更换核心动作。

### 5.4 辅助动作 A/B 轮换

- 每个训练日保留 A/B 轮换状态。第 15 章接入精选动作库后，A/B 表示轮换阶段，不再要求两份永久固定的完整动作清单。
- 每完成一轮 PPL，下一次同类训练自动切换 A/B。
- 默认每轮保留约 60%～70% 动作，替换约 30%～40%。
- 替换必须保持标准化后的主要训练肌群一致；单个动作允许改变动作模式，但最终整套计划必须保持必要结构平衡。

动作模式至少包括：

- 膝主导：深蹲、腿举、分腿蹲等。
- 髋主导：罗马尼亚硬拉、臀推等。
- 水平推：卧推、哑铃推举等。
- 垂直推：肩推类动作。
- 水平拉：划船类动作。
- 垂直拉：引体向上、高位下拉等。
- 屈膝、髋外展、提踵、肘屈伸等辅助模式。

系统不能用训练刺激高度重复的动作堆满计划，也不能为追求变化而随机替换全部动作。

### 5.5 当天状态输入

生成前必须确认：

- 推荐训练部位。
- 身体状态。
- 可用时间。
- 训练环境。
- 酸痛或不适部位。
- 今天希望避开的动作。

除训练部位外，其余项目优先使用快捷选项；不适部位和避开动作允许补充文字。

### 5.6 状态适配

- 状态良好：保留核心动作，并按历史表现提出渐进建议。
- 一般疲劳：降低建议重量或减少训练量，优先选择稳定性较高的动作。
- 明显疲劳：保留必要动作并缩短计划，不主动追求加重。
- 局部酸痛：降低相关部位训练量，或更换为负担较小的同模式动作。
- 明确不适：排除相关动作并提示谨慎训练，不进行伤病诊断。
- 器械不可用：从同主要肌群的合格替代池选择动作，并重新检查整套计划结构。

### 5.7 渐进负荷建议

- 全部完成且评价“轻松”：建议小幅增加重量或次数。
- 全部完成且评价“合适”：优先维持重量，争取稳定完成。
- 未完成目标或评价“吃力”：维持或适当降低目标。
- 评价“不适”：不建议加重，并在下次生成时优先考虑替换。

系统必须说明建议依据。用户确认前，不得覆盖原有训练目标。

### 5.8 AI 职责与校验

本地规则先确定训练日、核心动作、结构平衡、数量和训练量边界。AI 只能在允许范围内：

- 选择辅助动作和变式。
- 结合状态调整组数、次数和建议重量。
- 生成调整理由。
- 补充热身、拉伸和饮食建议。

AI 返回后，程序必须校验动作数量、必要字段、整套计划结构、避开动作、用户器械和数值格式。不合规结果自动修正、重试或切换为本地计划。

## 6. 功能需求

### 6.1 生成前设置

- 默认选中系统推荐训练日，并显示推荐原因。
- 用户可以修改训练部位。
- 用户没有完成必填状态时，不发起 AI 请求。
- 用户提交后保留输入，生成失败时无需重新填写。

### 6.2 计划预览

每个动作显示：

- 动作名称及训练目的。
- 核心动作或辅助动作标识。
- 组数、次数、建议重量和休息时间。
- 与上一次同类训练相比的变化。
- 本次选择或替换理由。

用户可以：

- 锁定动作。
- 点击“换一个”选择同模式替代动作。
- 修改重量、次数和组数。
- 确认计划并开始训练。

替换单个动作不得导致整套计划重新生成，也不得改变其他已锁定动作。

### 6.3 训练执行

- 依次显示当前动作、当前组和目标数据。
- 可直接修改实际重量和次数。
- 完成本组后自动进入休息计时。
- 支持跳过休息、切换动作和跳过动作。
- 每次完成一组后立即保存训练进度。
- 刷新页面或临时退出后，重新进入可以恢复原训练位置。
- 训练开始后不再调用 AI。

### 6.4 动作反馈

每个动作结束后，用户必须可以选择：

- 轻松。
- 合适。
- 吃力。
- 不适。

选择“不适”时允许补充不适部位。未填写补充内容不阻断训练完成，但下次计划仍需把该动作标记为需要确认。

### 6.5 训练完成

- 保存实际组数、重量、次数、动作反馈和训练时长。
- 更新 PPL 周期。
- 更新核心动作阶段数据。
- 清除今日计划的“进行中”状态，但保留完整历史记录。
- 显示本次训练总结和下一次训练方向。

### 6.6 数据复盘

- 历史记录按日期倒序展示。
- 核心动作趋势可以按动作查看。
- 周统计包括训练次数、总组数、总容量、训练时长和完成率。
- 系统建议必须显示所依据的历史记录和反馈，不把推断写成已确认事实。

### 6.7 本地备用计划

当无 API Key、网络失败、余额不足、请求超时或 AI 结果持续不合规时：

1. 保留用户已填写的当天状态。
2. 按当前 PPL 日、A/B 轮换、历史重量和本地动作库生成计划。
3. 遵守不适部位、避开动作、器械和时间限制。
4. 明确显示“本次使用本地备用计划”。
5. 用户仍可预览、替换和修改后开始训练。

## 7. 数据需求

### 7.1 数据对象

- 个人档案。
- PPL 模板与动作库。
- A/B 方案与动作替代关系。
- 核心动作训练阶段。
- PPL 周期状态。
- 当天状态。
- 已生成计划。
- 进行中训练。
- 已完成训练。
- 动作反馈。
- AI 设置。
- 备份版本信息。

### 7.2 数据流

1. 读取个人档案、周期状态和同类训练历史。
2. 本地规则生成计划骨架。
3. 将骨架与当天状态交给 AI 适配。
4. 校验 AI 返回结果。
5. 用户确认后保存今日计划。
6. 训练过程中持续保存进度。
7. 完成后写入历史，更新周期和下次建议。

### 7.3 本地存储

- 所有数据默认保存在当前浏览器。
- 切换页面、刷新或临时退出不能丢失进行中训练。
- 已完成记录不得因重新生成计划而被覆盖。
- API Key 单独保存，不得写入网页代码。
- 清除浏览器数据可能造成记录丢失，设置页应提示定期备份。

### 7.4 导出备份

普通备份包括：

- 个人资料。
- 训练体系。
- 历史训练。
- 当前周期。
- 未完成训练。
- 动作反馈。
- 数据格式版本和导出时间。

普通备份不得包含 API Key。

### 7.5 导入恢复

- 导入前校验文件格式和版本。
- 展示备份时间、训练记录数量和用户标识。
- 用户确认后才执行恢复。
- 导入前自动生成当前数据的临时备份。
- 导入失败时保持原数据不变。
- 新设备恢复后需要重新填写 API Key。

## 8. 异常与边界处理

- 无 API Key：允许直接使用本地备用计划。
- 网络失败：不清除已填写状态，切换本地计划。
- AI 格式错误：自动重试一次；再次失败后使用本地计划。
- AI 给出被避开的动作：自动替换。
- AI 数字字段出现区间、空值或非数字：程序转换为合法目标或回退本地默认值，不显示 `NaN`。
- 训练中刷新：恢复当前动作、当前组、已完成记录和休息状态。
- 数据导入冲突：以用户确认的备份为恢复目标，同时保留导入前快照。
- 明确身体不适：提示停止相关动作并谨慎处理，不提供诊断或治疗建议。

## 9. 非功能需求

### 9.1 平台

- 手机浏览器优先。
- 支持添加到手机主屏幕。
- 保持移动端 Web App 形态，不在首期开发原生应用。

### 9.2 易用性

- 正常情况下，从打开首页到开始训练不超过约 2 分钟。
- 主要操作支持单手完成。
- 高频按钮具有足够触控面积。
- 数字输入支持直接输入和按钮增减。
- 训练中减少弹窗和长文本阅读。

### 9.3 可靠性

- 每组完成后即时保存。
- AI 不可用时不阻断核心训练闭环。
- 无效输入不得污染历史记录。
- 重新生成计划不得覆盖已完成训练。

### 9.4 隐私与安全

- API Key 仅保存在当前浏览器，不写入公开代码或普通备份。
- 不向用户暗示本地存储等同于加密存储。
- 当前版本不上传训练数据到自有服务器。

## 10. 版本优先级

### 10.1 P0：完整训练闭环

- PPL 训练日推荐。
- 当天状态和限制条件采集。
- 8～15 个动作的计划生成。
- 核心动作稳定与辅助动作 A/B 轮换。
- 计划预览、锁定、替换和修改。
- 训练记录、休息计时和动作反馈。
- 进行中训练恢复。
- 完成后更新历史和周期。
- AI 失败时生成本地备用计划。

### 10.2 P1：长期使用能力

- 核心动作 4～6 周训练阶段管理。
- 基于动作反馈的调整建议。
- 变化理由和建议依据。
- 核心动作趋势与周统计。
- 数据导出、导入和导入前保护。

### 10.3 P2：后续优化

- 扩充动作库和替代关系。
- 根据长期表现识别停滞。
- 自动安排减量周。
- 围度、体重和体脂趋势增强。
- 多设备同步或云端版本。

## 11. 验收标准

### 11.1 正常生成

用户完成状态选择后，系统推荐符合实际完成历史的 PPL 训练日，并生成 8～15 个具备动作、组数、次数、建议重量和休息时间的正式训练动作。

### 11.2 周期轮换

用户完成一轮推、拉、腿后，下一轮同类训练的核心动作保持稳定，辅助动作按 A/B 方案合理变化，动作替换率处于约 30%～40%。

### 11.3 状态适配

用户选择疲劳、不适部位或避开动作后，计划必须做出对应调整并显示原因；被明确避开的动作不能出现在最终计划中。

### 11.4 用户控制

用户可以锁定动作、替换单个动作并修改组数、次数和重量。替换单个动作不改变其他已锁定动作。

### 11.5 训练恢复

用户至少完成一组后刷新页面，重新进入训练时能够恢复当前动作、当前组和已完成记录，不产生重复记录。

### 11.6 动作反馈

用户完成动作并提交反馈后，下次同类训练能够读取该反馈，并提出有依据的维持、加重、减量或替换建议。

### 11.7 AI 异常

关闭网络或使用无效 API Key 时，系统不阻断训练，能够生成标识明确的本地备用计划。

### 11.8 数据保护

导出的备份可以恢复个人资料、训练体系、历史、周期、未完成训练和动作反馈；导出文件不包含 API Key；导入失败不改变现有数据。

### 11.9 效率

在 API 正常、档案已完成的情况下，用户从首页进入到确认计划并开始训练，目标用时不超过约 2 分钟。

### 11.10 移动端体验

核心流程可在手机浏览器单手完成；训练数字可稳定编辑；空值、区间和非数字输入不会显示 `NaN` 或写入历史记录。

## 12. 产品成功判断

首要成功标准不是功能数量，而是用户能够持续使用 IronTrack 完成以下闭环：

> 打开网页 → 接受或调整推荐 → 两分钟内确认计划 → 完成训练 → 留下足够反馈供下次调整。

当用户无需借助其他工具编排当天训练，并且系统能够在保持核心动作可追踪的同时提供合理变化，即视为产品核心价值成立。

2026-08-28 已按本 PRD 完成 P0 和 P1：规则与 AI 混合生成、PPL 推进、A/B 轮换、核心动作阶段、计划预览、训练恢复、动作反馈、数据复盘及本地备份恢复均已接入当前静态入口 `index.html`。

- 完成组、休息计时、刷新恢复和动作反馈。
- 完成训练后 PPL 从推日推进至拉日，并切换已完成训练日的 A/B 方案。
- 徒手环境生成完整计划。
- 膝部不适时过滤膝主导动作。
- 390px 手机宽度无横向溢出。

## 14. V1.1 UI 视觉改版需求

### 14.1 改版目标

在不改变训练逻辑、数据结构和历史数据的前提下，重新建立 IronTrack 的视觉系统和页面层级，使其更接近高级运动品牌的个人训练产品，同时保持训练现场的清晰、高效和单手可操作性。

本轮允许重新排版、调整按钮位置和减少不必要的卡片容器。按 2026-09-01 确认变更，删除“我的 → 知识库”占位入口及内容；除此之外不得删减现有功能入口，不得改变 PPL、动作轮换、AI 生成、训练记录、反馈、备份与恢复规则。

### 14.2 视觉方向

- 采用“午夜竞技”风格：近黑背景、暖白文字和荧光绿品牌主色。
- 只提供深色模式，本轮不增加浅色主题或主题切换。
- 荧光绿用于主要按钮、当前状态、进度和关键数字；警告、错误和成功状态可以使用独立语义色，但不得形成第二套品牌主色。
- 品牌名使用粗体大写；页面标题和关键训练数字强调力量感，普通说明文字保持简短清楚。
- 减少“所有内容都放入卡片”的表现，优先使用留白、字号、对齐和分隔线建立层级。
- 页面文案采用简短、有力量的语气，只在首页、训练开始和训练完成等关键时刻使用。

### 14.3 图片与品牌表达

- 登录页和今日首页使用低光环境中的真实训练人物照片，动作清楚但不突出面部。
- 计划、正式训练、数据和设置页面不使用大面积照片，以免影响阅读和操作。
- 正式资源必须随项目本地发布，不依赖运行时外部图片链接；图片中不得包含第三方品牌、文字或界面元素。
- 首页采用“品牌与效率平衡”布局：照片约占半屏，主训练入口清楚，首屏同时保留本周进度、连续训练和上次训练摘要。

### 14.4 页面布局

- 登录页：全屏训练人物背景；品牌、已有用户名和新用户名输入位于安全区域内。
- 今日首页：突出推荐训练日、简短口号和“生成今日计划”，同时展示本周状态和上次训练。
- 训练体系页：以 PPL 周期时间线为主，分层展示核心动作、A/B 方案和训练阶段。
- 生成前设置页：快捷选项分组，必填状态、不适提示和选中状态清楚区分。
- 计划预览页：核心动作优先，辅助动作使用简洁列表；保留锁定、替换及数字编辑。
- 训练执行页：采用“单组专注”布局，突出当前动作、重量、次数和完成按钮。
- 数据页：优先展示本周统计、核心动作趋势和按时间排列的训练历史。
- 我的页面：身体资料、器械、API 和本地备份分区展示，保持工具化表达。
- 底部导航保留中央训练按钮，其他四个入口降低视觉权重。

### 14.5 训练页与底部安全区

现有版本在 390×844 视口、页面位于顶部时，“完成本组”按钮与固定底部导航存在约 40px 重叠，用户需要下滑才能完成操作。V1.1 必须修复该问题。

- “完成本组”等训练主操作固定在底部导航上方，无需下滑即可操作。
- 页面底部留白统一按“导航栏高度 + 系统安全区 + 额外间距”计算。
- 次要操作降低视觉权重，必要时收纳到“更多操作”，但功能不得删除。
- 虚拟键盘打开时，当前输入框必须保持可见；固定操作区不得遮挡输入框。
- 重量和次数继续支持直接输入，左右调整按钮继续保留，并沿用现有调整规则。

### 14.6 响应式与可访问性

- 动作名称和关键数字在完整显示的前提下尽量放大。
- 长动作名称最多两行；文字和数字不得裁切、重叠、异常换行或被底栏遮挡。
- 可点击区域不小于 44px，保证训练时单手操作。
- 页面不得产生横向溢出。
- 至少验收 320×568、375×667 和 390×844 三种视口。
- 页面应正确处理手机刘海、底部手势区域和虚拟键盘。

### 14.7 动效

- 首页照片、标题和数据模块采用较明显的分层进入动画。
- 页面切换、进度和数字变化具有统一的运动节奏。
- 重量、次数、计时和主要训练按钮必须即时响应，不得为动画等待。
- 系统启用“减少动态效果”时，自动移除大幅移动和连续动画，只保留必要状态反馈。

### 14.8 数据与兼容边界

- 继续使用现有本地存储键和数据结构，UI 改版不引入数据迁移。
- 发布不得清除个人资料、训练历史、周期状态、今日计划或进行中的训练。
- API Key继续由用户自行填写，不写入代码，也不进入普通备份。
- 现有训练计划生成、动作替换、反馈、数据导入导出及刷新恢复能力必须完成回归测试。

### 14.9 UI 改版验收

1. 登录、首页、训练体系、训练设置、计划预览、训练执行、数据和我的页面使用同一套视觉系统。
2. 首页首屏具有明确品牌视觉，同时能看到主要训练入口和关键训练状态。
3. 训练执行页的动作名称、重量、次数和完成按钮在目标视口中完整显示。
4. 固定底栏不覆盖主按钮、次要操作或正文；“完成本组”无需下滑即可点击。
5. 虚拟键盘打开后，正在编辑的重量或次数输入框保持可见。
6. 动画明显但不延迟训练操作；减少动态效果设置生效。
7. 原有本地数据、AI 计划、本地备用计划、训练恢复、动作反馈和备份恢复均正常。
8. 线上资源不依赖外部图片地址，静态检查、窄屏验收和主要训练闭环全部通过后方可发布。

详细页面和实施规格见 `docs/superpowers/specs/2026-08-31-irontrack-ui-redesign-design.md`。

### 14.10 添加到主屏幕与应用图标

- iPhone Safari 添加到主屏幕后，图标采用“午夜竞技”风格：近黑底、荧光绿简化杠铃和小面积暖白圆心。
- 图标内不放置难以辨认的小字；关键图形必须位于安全区内，系统圆角或遮罩裁切后仍完整、居中和清晰。
- 页面必须显式声明 iPhone 主屏幕图标，并使用有效的 Web App 清单；图标资源随项目本地发布，不依赖外部地址。
- 至少提供 iPhone 所需的 `180×180` 图标，以及 Web App 清单所需的 `192×192`、`512×512` 和 maskable 图标。
- 主屏幕名称为 `IronTrack`，从主屏幕打开后保持独立 Web App 显示方式，主题色与现有近黑界面一致。
- 图标或清单修改不得清除个人资料、训练计划、历史记录、进行中训练或 API Key。
- 验收前必须先从“我的 → 本地备份”导出备份，再删除已有旧图标并重新添加，以排除 iOS 图标缓存。程序不得主动清除本地数据，但也不得承诺不同 iOS 版本或安装方式下删除主屏幕 Web App 一定保留数据；异常时应使用备份恢复。

详细实施规格见 `docs/superpowers/specs/2026-09-01-irontrack-home-screen-icon-design.md`。

## 15. 精选动作库与智能变式

### 15.1 目标与范围

- 固定使用 `hasaneyldrm/exercises-dataset` 的已审核版本，从 1,324 条记录中精选约 200～300 个服务 PPL 力量训练及当前器械环境的动作。
- 保留现有核心动作、PPL、单次 8～15 个动作、历史反馈和本地备用计划规则。
- 本阶段不导入图片与 GIF，不增加完整动作库页面、后台服务或运行时 GitHub 请求。

### 15.2 动作数据

- 每个动作必须具有稳定编号、常见中文名称、英文名称、中文别名、PPL归属、主要及辅助肌群、单一替换匹配肌群、动作模式、器械、保守不适过滤标签、替代组、推荐状态、中文步骤和无历史时使用的默认训练量。
- 数据源未提供的 IronTrack 专用字段必须经过转换和人工审核，不能由 AI 临时生成后直接作为正式数据。
- 新记录保存稳定编号和名称快照；旧历史只在唯一匹配时补充关联，歧义和无法识别的记录保持原样。
- 动作库版本、暂停推荐列表和动作选择偏好进入普通备份；API Key继续排除。

### 15.3 变化规则

- 核心动作正常保持 4～6 周，AI不得自行更换锁定动作。
- 保留 A/B 周期状态作为辅助动作轮换阶段，不再把 A/B 固定为两份永久不变的动作清单。
- 每次同类训练只替换约 30%～40% 的辅助动作；替换候选优先避开最近两次同类训练使用过的动作。
- 单个动作替换必须保持标准化后的单一替换匹配肌群一致，允许动作模式变化；最终整套计划必须保持必要结构平衡。
- 本地规则先按审核状态、PPL、肌群、器械、不适、用户避开、暂停推荐和结构平衡过滤候选；AI只能在合格候选内选择和解释。
- 候选不足时复用最久未出现的合格动作，不放宽器械、不适或暂停推荐条件。

### 15.4 反馈与用户控制

- “不适”动作暂停推荐，直到用户在“我的”中手动恢复。
- “吃力”只调整重量、次数或组数，不因连续吃力自动换动作。
- “轻松”动作在下次同类计划预览中显示“继续进阶 / 换个变式”，默认继续进阶。
- 新动作可以进入计划预览，但必须标记“新动作”，说明选择理由，并在预览和正式训练中提供可展开中文步骤。
- 替换单个动作不得改变其他动作或锁定核心动作。

### 15.5 数据、授权与异常边界

- 兼容升级只补充字段，升级前生成恢复快照，不清空或覆盖现有训练数据。
- 精选动作库加载失败时使用当前内置动作库；中文步骤缺失不阻断训练；AI越界时回退本地候选或本地计划。
- 只使用 MIT 许可覆盖的数据和说明文字；不复制、发布或运行时加载上游图片与 GIF。
- 中文名称和说明必须完成术语校对；数据集内容不得作为伤病诊断、康复处方或安全保证。
- 上游更新必须固定新版本并重新审核，不能自动同步覆盖。

### 15.6 实施门槛与验收

- 先完成动作去重、PPL与器械分类、中文校对和用户分类审核，再进入程序接入。
- 现有历史、反馈、进行中训练和备份恢复必须通过兼容验收。
- 同类训练的辅助动作轮换率、近期重复控制、结构平衡、器械过滤、不适暂停和“轻松”选择必须分别验证。
- 无 API、AI异常和动作库失败时仍能完成本地计划与训练闭环。
- 手机不得在首屏加载完整上游数据或未授权媒体，现有加载速度、底部安全区和训练操作不得退化。

详细设计见 `docs/superpowers/specs/2026-09-02-irontrack-exercise-catalog-variation-design.md`。
