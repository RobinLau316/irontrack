## 1. 产品目标

IronTrack 是一个持续带用户训练的 AI 私人教练。教练了解用户的目标、经验、身体限制和现实条件，主动提出阶段训练路线与当天安排，逐组教学和记录，训练后总结表现并调整后续计划。用户用日常语言表达目标、确认事实和实际训练，并可随时做小幅调整；不要求用户掌握健身术语或自行编排训练。

产品根据真实记录循序渐进，不以每天随机换动作代替计划；训练数据仅保存在用户当前浏览器。应用不诊断或治疗伤病。

## 2. 用户和教练职责

教练主动了解、规划、讲解、带练、跟进和复盘。用户确认教练对自己的理解、确认阶段安排、确认每组真实完成数据，并在遇到困难或不适时表达。教练主动完成日常动作、组数、次数和重量调整并简要说明；阶段目标、每周频率或整体训练安排明显变化时，必须提出建议并等待用户确认。

## 3. 首次了解

新用户首次进入时以自然对话表达目标。教练结合回答和已有资料，按需了解训练经历、每周时间、场地与器械、身体限制、偏好及必要个人特征。每次只问一个重点；已知信息不重复问；未知事实不猜测。

信息足够后，教练形成简短理解摘要，明确已知与待了解内容。用户可纠正摘要；确认后教练提出阶段安排，解释目标、每周大致安排、训练重点、进步依据和复盘时间。用户可以小幅修改并确认。新手不足以判断的情况在后续训练逐渐了解。

已有用户先使用本地档案和实际训练记录，再补充缺失信息。升级不得删除个人档案、历史、归档或进行中的训练。旧版未开始预览可以清理；已开始的训练必须允许继续。

## 4. 每日跟进和计划

用户打开程序后，教练根据未完成训练、上次记录、最近训练间隔和当前阶段确定下一步。应用不在关闭状态下发送提醒。日常训练开始前简短了解可用时间、疲劳、不适及自由表达的重点，并确认当天器械条件。

AI 根据阶段目标、已确认档案、近期真实完成的组记录与反馈、用户熟悉度、器械、时间及当天状态直接生成完整计划。AI 不受固定 PPL 模板和动作目录限制；需保持合理连续性、避免目的相同的近似动作堆叠，并说明各动作选择的作用和依据。计划须先预览，用户确认后才开始；用户可通过日常语言小修小改。取消预览不写训练记录。

若 AI 不可用、返回无效内容或未通过程序合理性检查，明确提示失败并允许重试；不得显示旧固定模板并称其为 AI 计划。已保存历史不受影响。

## 5. 动作教学

新计划动作使用易理解的通俗中文名称，并说明所需器械、训练部位或作用。每个动作包括简短可执行的分步骤说明：准备姿势、动作过程和关键注意点。对用户陌生的动作提供更详细教学；用户可说“不会做”“太复杂”“换一个”。

已确认弃用现有动作目录作为计划生成、安全候选与运行时教学依据。旧目录及旧动作引用可留作归档/历史兼容，但不再加载到新计划流程。AI 教学文字需具备程序结构校验和清晰内容；文字说明不代表系统观察过用户现场动作。

## 6. 逐组带练与数据

开始后以当前动作和当前组为主。动作开始前说明做法；每组开始前显示建议重量和次数；完成后只让用户确认或修正实际重量和次数，不强制选择感受。休息时可显示计时。用户随时可以说明太重、不会做、器械不可用或时间变短，由教练更新当天后续安排。

刷新、离开或跨日后保留当前动作、组次和已确认组。计划值与实际值必须分离，只有用户确认的真实组进入历史和后续表现分析。用户中断训练时不虚构完成组，也不丢失已经确认的组。

## 7. 训练复盘与后续调整

训练结束后，程序自动汇总实际完成内容，只用一个可跳过的自由文本反馈入口。训练记录先成功保存在本地，再由教练根据阶段安排和连续的真实记录给出简短复盘：完成了什么、有哪些有据可查的变化、哪些仍待观察、下次如何安排。数据不足时明说不足；计划目标不能作为实际表现。

AI 调用失败不能影响训练保存。日常细节由教练自动调整；显著阶段调整作为待确认建议展示，用户确认后才更新阶段规划。

## 8. AI 数据使用与隐私

AI 直接使用本机配置的 DeepSeek API Key。首次发送前明确提示将传输给 DeepSeek 的资料：用户输入、训练档案、身体限制、当天状态及近期真实训练记录；姓名不发送。未确认前不得发出请求。API Key 单独保存在浏览器，不进入代码或普通备份。

## 9. 页面组织

主要入口按用户工作收敛为：

- **今天**：教练跟进、计划预览、逐组训练和训练复盘。
- **路线**：用户确认的教练理解、阶段目标、每周安排及待确认建议。
- **我的进展**：实际训练、组数、训练时长、身体记录与阶段回顾。

档案、动作教学、备份和 AI Key 设置支持以上主流程。

## 10. 兼容和发布

保留 `localStorage` 既有档案、计划、历史、归档、身体数据、备份和恢复快照；兼容 V1/V2/V3 备份。保留既有动作名以便查看历史，不再用它们生成新计划。每次发布递增 Service Worker `CACHE_VERSION`。推送 `main` 触发 GitHub Pages 部署。

## 11. 验收标准

- 新用户能自由表达目标；对话草稿可恢复；教练能逐步补问并展示可确认理解摘要。
- 确认摘要后教练主动提出阶段计划；用户确认或微调后才能开始每日训练流程。
- 已有用户复用档案和真实历史；进行中的旧训练可以续练。
- 新日计划不加载旧动作库、不固定 PPL 选择，按档案与当天资料生成；动作名称通俗，教学步骤可读。
- 计划可预览和自然语言微调，用户确认后逐组训练；每组不强制填写感受。
- 只有实际确认组进入训练记录；训练保存后 AI 复盘；AI 故障不丢训练。
- 阶段重要变化等待用户确认；常规调整自动完成并说明。
- 发送训练数据前明确告知 DeepSeek 接收范围并取得用户确认。
- `npm run build`、`git diff --check`、移动端布局及既有记录/备份兼容检查通过。真实 AI 和实机验收单独报告。

## 历史需求（已被 V1.3 取代）：V1.1 UI 视觉改版

### 14.1 改版目标

在不改变训练逻辑、数据结构和历史数据的前提下，重新建立 IronTrack 的视觉系统和页面层级，使其更接近高级运动品牌的个人训练产品，同时保持训练现场的清晰、高效和单手可操作性。

本轮允许重新排版、调整按钮位置和减少不必要的卡片容器。按 2026-09-01 确认变更，删除“我的 → 知识库”占位入口及内容；除此之外不得删减现有功能入口，不得改变 PPL、动作轮换、AI 生成、训练记录、反馈、备份与恢复规则。

### 14.2 视觉方向

- 采用“午夜竞技”风格：近黑背景、暖白文字和荧光绿品牌主色。
- 只提供深色模式，本轮不增加浅色主题或主题切换。
- 荧光绿用于主要按钮、当前状态、进度和关键数字；警告、错误和成功状态可以使用独立语义色，但不得形成第二套品牌主色。
- 品牌名使用粗体大写；页面标题和关键训练数字强调力量感，普通说明文字保持简短清楚。
- 减少“所有内容都放入卡片”的表现，优先使用留白、字号、对齐和分隔线建立层级。
- 页面文案采用简短、有力量的语气，只在首页、训练开始和训练完成等关键时刻使用。

### 14.3 图片与品牌表达

- 登录页和今日首页使用低光环境中的真实训练人物照片，动作清楚但不突出面部。
- 计划、正式训练、数据和设置页面不使用大面积照片，以免影响阅读和操作。
- 正式资源必须随项目本地发布，不依赖运行时外部图片链接；图片中不得包含第三方品牌、文字或界面元素。
- 首页采用“品牌与效率平衡”布局：照片约占半屏，主训练入口清楚，首屏同时保留本周进度、连续训练和上次训练摘要。

### 14.4 页面布局

- 登录页：全屏训练人物背景；品牌、已有用户名和新用户名输入位于安全区域内。
- 今日首页：突出推荐训练日、简短口号和“生成今日计划”，同时展示本周状态和上次训练。
- 训练体系页：以 PPL 周期时间线为主，分层展示核心动作、A/B 方案和训练阶段。
- 生成前设置页：快捷选项分组，必填状态、不适提示和选中状态清楚区分。
- 计划预览页：核心动作优先，辅助动作使用简洁列表；保留锁定、替换及数字编辑。
- 训练执行页：采用“单组专注”布局，突出当前动作、重量、次数和完成按钮。
- 数据页：优先展示本周统计、核心动作趋势和按时间排列的训练历史。
- 我的页面：身体资料、器械、API 和本地备份分区展示，保持工具化表达。
- 底部导航保留中央训练按钮，其他四个入口降低视觉权重。

### 14.5 训练页与底部安全区

现有版本在 390×844 视口、页面位于顶部时，“完成本组”按钮与固定底部导航存在约 40px 重叠，用户需要下滑才能完成操作。V1.1 必须修复该问题。

- “完成本组”等训练主操作固定在底部导航上方，无需下滑即可操作。
- 页面底部留白统一按“导航栏高度 + 系统安全区 + 额外间距”计算。
- 次要操作降低视觉权重，必要时收纳到“更多操作”，但功能不得删除。
- 虚拟键盘打开时，当前输入框必须保持可见；固定操作区不得遮挡输入框。
- 重量和次数继续支持直接输入，左右调整按钮继续保留，并沿用现有调整规则。

### 14.6 响应式与可访问性

- 动作名称和关键数字在完整显示的前提下尽量放大。
- 长动作名称最多两行；文字和数字不得裁切、重叠、异常换行或被底栏遮挡。
- 可点击区域不小于 44px，保证训练时单手操作。
- 页面不得产生横向溢出。
- 至少验收 320×568、375×667 和 390×844 三种视口。
- 页面应正确处理手机刘海、底部手势区域和虚拟键盘。

### 14.7 动效

- 首页照片、标题和数据模块采用较明显的分层进入动画。
- 页面切换、进度和数字变化具有统一的运动节奏。
- 重量、次数、计时和主要训练按钮必须即时响应，不得为动画等待。
- 系统启用“减少动态效果”时，自动移除大幅移动和连续动画，只保留必要状态反馈。

### 14.8 数据与兼容边界

- 继续使用现有本地存储键和数据结构，UI 改版不引入数据迁移。
- 发布不得清除个人资料、训练历史、周期状态、今日计划或进行中的训练。
- API Key继续由用户自行填写，不写入代码，也不进入普通备份。
- 现有训练计划生成、动作替换、反馈、数据导入导出及刷新恢复能力必须完成回归测试。

### 14.9 UI 改版验收

1. 登录、首页、训练体系、训练设置、计划预览、训练执行、数据和我的页面使用同一套视觉系统。
2. 首页首屏具有明确品牌视觉，同时能看到主要训练入口和关键训练状态。
3. 训练执行页的动作名称、重量、次数和完成按钮在目标视口中完整显示。
4. 固定底栏不覆盖主按钮、次要操作或正文；“完成本组”无需下滑即可点击。
5. 虚拟键盘打开后，正在编辑的重量或次数输入框保持可见。
6. 动画明显但不延迟训练操作；减少动态效果设置生效。
7. 原有本地数据、AI 计划、本地备用计划、训练恢复、动作反馈和备份恢复均正常。
8. 线上资源不依赖外部图片地址，静态检查、窄屏验收和主要训练闭环全部通过后方可发布。

详细页面和实施规格见 `docs/superpowers/specs/2026-08-31-irontrack-ui-redesign-design.md`。

- 图标内不放置难以辨认的小字；关键图形必须位于安全区内，系统圆角或遮罩裁切后仍完整、居中和清晰。
- 页面必须显式声明 iPhone 主屏幕图标，并使用有效的 Web App 清单；图标资源随项目本地发布，不依赖外部地址。
- 至少提供 iPhone 所需的 `180×180` 图标，以及 Web App 清单所需的 `192×192`、`512×512` 和 maskable 图标。
- 主屏幕名称为 `IronTrack`，从主屏幕打开后保持独立 Web App 显示方式，主题色与现有近黑界面一致。
- 图标或清单修改不得清除个人资料、训练计划、历史记录、进行中训练或 API Key。
- 验收前必须先从“我的 → 本地备份”导出备份，再删除已有旧图标并重新添加，以排除 iOS 图标缓存。程序不得主动清除本地数据，但也不得承诺不同 iOS 版本或安装方式下删除主屏幕 Web App 一定保留数据；异常时应使用备份恢复。

## 历史需求（已被 V1.3 取代）：精选动作库与智能变式

### 15.1 目标与范围

- 固定使用 `hasaneyldrm/exercises-dataset` 的已审核版本，从 1,324 条记录中精选约 200～300 个服务 PPL 力量训练及当前器械环境的动作。
- 保留现有核心动作、PPL、单次 8～15 个动作、历史反馈和本地备用计划规则。
- 本阶段不导入图片与 GIF，不增加完整动作库页面、后台服务或运行时 GitHub 请求。

### 15.2 动作数据

- 每个动作必须具有稳定编号、常见中文名称、英文名称、中文别名、PPL归属、主要及辅助肌群、单一替换匹配肌群、动作模式、器械、保守不适过滤标签、替代组、推荐状态、中文步骤和无历史时使用的默认训练量。
- 数据源未提供的 IronTrack 专用字段必须经过转换和人工审核，不能由 AI 临时生成后直接作为正式数据。
- 新记录保存稳定编号和名称快照；旧历史只在唯一匹配时补充关联，歧义和无法识别的记录保持原样。
- 动作库版本、暂停推荐列表和动作选择偏好进入普通备份；API Key继续排除。

### 15.3 变化规则

- 核心动作正常保持 4～6 周，AI不得自行更换锁定动作。
- 保留 A/B 周期状态作为辅助动作轮换阶段，不再把 A/B 固定为两份永久不变的动作清单。
- 每次同类训练只替换约 30%～40% 的辅助动作；替换候选优先避开最近两次同类训练使用过的动作。
- 单个动作替换必须保持标准化后的单一替换匹配肌群一致，允许动作模式变化；最终整套计划必须保持必要结构平衡。
- 本地规则先按审核状态、PPL、肌群、器械、不适、用户避开、暂停推荐和结构平衡过滤候选；AI只能在合格候选内选择和解释。
- 候选不足时复用最久未出现的合格动作，不放宽器械、不适或暂停推荐条件。

### 15.4 反馈与用户控制

- “不适”动作暂停推荐，直到用户在“我的”中手动恢复。
- “吃力”只调整重量、次数或组数，不因连续吃力自动换动作。
- “轻松”动作在下次同类计划预览中显示“继续进阶 / 换个变式”，默认继续进阶。
- 新动作可以进入计划预览，但必须标记“新动作”，说明选择理由，并在预览和正式训练中提供可展开中文步骤。
- 替换单个动作不得改变其他动作或锁定核心动作。

### 15.5 数据、授权与异常边界

- 兼容升级只补充字段，升级前生成恢复快照，不清空或覆盖现有训练数据。
- 精选动作库加载失败时使用当前内置动作库；中文步骤缺失不阻断训练；AI越界时回退本地候选或本地计划。
- 只使用 MIT 许可覆盖的数据和说明文字；不复制、发布或运行时加载上游图片与 GIF。
- 中文名称和说明必须完成术语校对；数据集内容不得作为伤病诊断、康复处方或安全保证。
- 上游更新必须固定新版本并重新审核，不能自动同步覆盖。

### 15.6 实施门槛与验收

- 先完成动作去重、PPL与器械分类、中文校对和用户分类审核，再进入程序接入。
- 现有历史、反馈、进行中训练和备份恢复必须通过兼容验收。
- 同类训练的辅助动作轮换率、近期重复控制、结构平衡、器械过滤、不适暂停和“轻松”选择必须分别验证。
- 无 API、AI异常和动作库失败时仍能完成本地计划与训练闭环。
- 手机不得在首屏加载完整上游数据或未授权媒体，现有加载速度、底部安全区和训练操作不得退化。

详细设计见 `docs/superpowers/specs/2026-09-02-irontrack-exercise-catalog-variation-design.md`。

## 历史需求（已被 V1.3 取代）：V1.2 规则主导训练计划重构

### 16.1 变更目标

V1.2 将训练计划生成从“规则生成骨架、AI 做适配”调整为“本地规则直接生成完整计划、AI 只做解释和评价”。本次变更的目标是降低 API 返回不稳定对训练闭环的影响，减少专业但低频的冗余功能，让用户打开网页后更稳定地得到当天可执行训练安排。

该章记录 V1.2 当时的重构需求和实施方案。自 V1.3 起，AI 已作为可选计划适配重新进入计划生成流程；以本文第 1～12 章为当前需求。

### 16.2 产品边界

- IronTrack 继续面向产品所有者本人：有一定力量训练经验，采用 PPL 分化，主要在健身房训练。
- 基础训练计划由固定 PPL 模板、本地动作白名单、历史记录和当天状态计算生成。
- AI 不参与基础计划生成，不作为动作选择、训练量、周期推进或合理性判断的前置条件。
- AI 只在用户需要时用于解释计划、查看动作示范说明、训练后评价和后续指导。
- 用户保留手动调整权限，可以根据器械占用、身体状态和个人偏好替换动作或修改组数、次数、重量和休息时间。

### 16.3 PPL 单次训练结构

每次训练默认约 8 个正式训练动作，目标训练时长为 45～60 分钟。系统通过组数、重量、次数和休息时间控制训练量，不以增加大量动作作为常规方案。

Push 日默认结构：

- 胸部 3 个。
- 肩部 2 个。
- 三头 2 个。
- 机动 1 个。

Pull 日默认结构：

- 背部垂直拉 2 个。
- 背部水平拉 2 个。
- 后束 / 上背 1 个。
- 二头 2 个。
- 机动 1 个。

Leg 日默认结构：

- 股四头主导 2 个。
- 髋主导 / 臀腿后侧 2 个。
- 单侧稳定 1 个。
- 小腿 1 个。
- 核心 1 个。
- 机动 1 个。

机动位用于补弱项、处理器械占用、替换不适动作或根据当天状态降低强度。机动位不得破坏当日主要结构。

### 16.4 动作白名单

项目可以保留已引入的开源动作库作为数据来源和后台资料，但自动训练计划只从固化后的 PPL 动作白名单中选择。

白名单规模暂定为每个 PPL 训练日约 20 个候选动作，总规模约 60 个动作。当天实际训练仍只安排约 8 个动作。

白名单筛选原则：

- 优先选择健身房常见器械能完成的动作。
- 优先选择名称直观、动作路径清楚、容易学习的动作。
- 优先选择适合有一定基础的初级训练者长期执行的动作。
- 暂不自动推荐技术门槛高、风险不好判断、动作名称花哨或过度细分的动作。
- 白名单外动作可以作为资料保留，但不进入自动训练计划。

白名单不再拆分“常用推荐”和“可选变式”等复杂等级。后续开发只需维护一份可进入自动计划的合格动作池。

### 16.5 周期与轮换规则

- Push、Pull、Leg 三次训练构成一个 PPL 小周期。
- 3 个 PPL 小周期构成一个动作稳定期，即约 9 次训练后再评估主动作轮换。
- 主动作在稳定期内保持稳定，便于比较重量、次数、完成度和身体反馈。
- 辅助动作可以变化更快，用于覆盖肌群、适配器械和增加训练趣味性。
- 系统优先保证主动作质量和周期稳定；如果训练时长、疲劳感或完成度异常，优先减少辅助动作或降低辅助训练量，而不是频繁改动主动作。
- 连续未完成目标、明确不适、器械不可用或用户主动调整时，才允许提前触发主动作替换建议。

### 16.6 AI 介入场景

AI 入口从“生成基础计划”调整为以下轻量辅助场景：

- 计划解释：说明当天为什么练这个训练日、为什么采用当前动作结构和训练量。
- 动作示范：提供动作要点、发力提示、常见错误和保守注意事项。
- 训练评价：基于已完成记录、动作反馈、训练时长、完成率和本地计算结果评价本次训练。
- 后续指导：在规则结果基础上解释下次维持、加重、减量、减少辅助动作或替换动作的原因。
- 异常建议：在用户反馈疲劳、不适或连续完成不好时，给出保守建议，但不得进行诊断或治疗承诺。

AI 输出只能作为解释和建议展示。任何会影响训练计划的动作、组数、次数、重量或休息时间变化，都必须先通过本地规则校验，并由用户确认。

### 16.7 前端影响

- 计划生成入口不再以 API Key、网络或 AI 成功为前提。
- 生成前设置页继续收集训练日、状态、可用时间、训练环境、不适部位和避开动作，但提交后优先进入本地规则生成。
- 计划预览页应显示规则来源、PPL 结构分配、主动作稳定原因、辅助动作选择原因和手动替换入口。
- AI 相关入口应调整为“解释”“动作要点”“训练评价”“后续建议”等语义，不再表达为基础计划生成能力。
- 无 API Key 或 AI 失败时，不显示阻断式错误；仅在用户点击 AI 辅助内容时提示该解释或评价暂不可用。
- 页面应继续保持训练现场优先：当天怎么练、当前动作、重量、次数和完成按钮优先级高于长文本说明。

### 16.8 数据与规则影响

- 需要维护本地 PPL 白名单动作池、动作结构槽位、主动作稳定期状态、辅助动作轮换记录和用户手动调整记录。
- 现有 `localStorage` 中的个人档案、计划、历史、进行中训练、动作反馈、周期状态和 API Key 必须继续兼容。
- 旧历史中的动作名称和统计记录不得因白名单缩减而丢失；无法匹配白名单的旧动作保留历史展示，但不进入新的自动计划。
- 备份导出应包含白名单版本、主动作稳定期、周期状态、历史记录、动作反馈和用户调整记录；继续排除 API Key。
- 训练记录和基础复盘不得依赖 AI 返回。训练完成后，系统先保存结构化记录并计算基础结论，再允许 AI 基于结论生成评价文字。

### 16.9 开发实施建议

为降低改动风险，本次重构建议按以下顺序实施：

1. 先抽出本地计划生成规则，保证无 API 时能直接生成符合 PPL 结构的约 8 个动作计划。
2. 固化 PPL 白名单和三类训练日槽位，不再让自动计划读取完整开源动作库。
3. 调整计划预览和训练体系页文案，使用户看到的是规则计划、结构原因和手动替换入口。
4. 将 AI 调用从计划生成链路中移出，改为解释、动作要点、训练评价和后续建议的按需入口。
5. 补齐旧数据兼容和备份字段，确保已有训练记录、进行中训练和周期状态不被清空。
6. 回归测试计划生成、动作替换、训练执行、刷新恢复、训练完成、数据复盘、备份导入导出和无 API 场景。

### 16.10 验收标准

1. 未设置 API Key、网络失败或 AI 请求失败时，用户仍能生成当天 PPL 计划，并完成训练记录。
2. Push、Pull、Leg 计划默认约 8 个动作，结构分别符合第 16.3 节的分配。
3. 自动计划只从 PPL 白名单动作池中选择动作；白名单外动作不进入新计划。
4. 每个 PPL 训练日约 20 个候选动作，总白名单约 60 个动作。
5. 主动作在约 9 次训练的稳定期内保持，不因追求变化而频繁替换。
6. 辅助动作可以轮换，但不得破坏当日 PPL 结构，也不得堆叠重复刺激。
7. 疲劳、训练超时或完成度异常时，系统优先减少辅助训练量或降低辅助动作强度。
8. 用户可以手动替换动作和修改训练数字，替换优先限定在同训练日、同肌群或相近训练目的的白名单动作中。
9. 训练开始后不调用 AI；刷新或临时退出后可以恢复当前动作、当前组和已完成记录。
10. 训练完成后先保存结构化记录和本地统计，再按需调用 AI 生成评价或指导。
11. AI 入口只用于解释、示范、评价和指导，不再作为基础计划生成按钮或必要流程。
12. 旧历史、个人档案、当前周期、进行中训练和普通备份恢复均保持可用。
