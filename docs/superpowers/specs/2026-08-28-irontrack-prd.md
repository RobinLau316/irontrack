## 1. 产品目标与当前状态

IronTrack 是个人长期使用的手机优先 Web 健身记录工具。它沿着一个持续数周的 PPL 训练方向，根据当天时间、疲劳、不适和真实训练表现调整计划，帮助用户用较少选择开始训练，并留下准确、可供后续调整的记录。

V1.3 已上线的范围包括：简短训练档案、当天三问、本地 PPL 计划、可选 AI 计划适配、计划预览与调整、逐组实际记录、部分训练结束选择、历史与周统计、本地备份恢复。首要判断标准是训练是否能连贯完成、记录是否可信、训练前操作是否简单。

状态说明：本地自动检查和桌面浏览器中的训练闭环已通过；真实 iPhone 的添加到主屏幕、锁屏恢复和文件导入导出尚未实机验收。自由语言自动解析并改写结构化档案字段也尚未实现，当前以可编辑档案字段和自由文本备注保存用户信息。

## 2. 用户与产品边界

### 2.1 目标用户

核心用户为产品所有者本人，力量训练经验可以从初学到有一定基础。用户不需要理解训练术语，也不需要每天自行安排 PPL 动作。默认训练场地是器械齐全的健身房。

### 2.2 产品原则

1. 训练方向按数周保持连续，单次计划根据实际表现和恢复情况小步调整。
2. 优先适配用户当天可用时间，减少辅助动作；一份计划最多 8 个正式训练动作。
3. 训练记录是核心。计划目标和实际完成分开保存，只有用户确认的组才是实际组数据。
4. 未完成训练保留在历史，但不冒充完整训练；部分训练已确认的组仍用于实际组统计和后续判断。
5. 本地规则保证无 AI 时可以生成和完成训练。AI 是用户可主动开启的计划适配能力，不是运行前提。
6. 训练数据默认只存在当前浏览器；数据保护、备份与恢复优先于复杂架构。
7. 产品不诊断或治疗伤病；遇到明显疼痛或异常症状，界面提示停止相关动作并谨慎处理。

### 2.3 非目标

当前不建设用户注册、教练协作、云端同步、订阅运营、原生 iOS/Android 应用、营养跟踪或医疗康复能力。无需为个人单机工具引入后端或复杂框架。

## 3. 核心使用流程

1. **首次了解**：新用户按顺序回答训练方向、每周频率、训练经验、长期疼痛或动作限制；信息足够时可以跳过，回答草稿逐题保存在本地。旧用户不重复接受问卷。
2. **每次训练前**：只询问今天能练多久、疲劳程度、有无疼痛或不适。场地默认健身房，不提供器械配置选择。
3. **生成计划**：本地规则结合训练档案、PPL 下一训练日、当天回答和历史实际记录生成计划。用户开启可选 AI 并配置 API Key 时，AI 才可以适配本地计划。
4. **查看与调整**：用户查看动作和目标数字，可换动作、修改目标，或在启用 AI 时用日常语言提出调整。说明保持简短；意思不清楚时才追问。
5. **确认并训练**：用户确认计划后开始训练。每组默认带入计划重量和次数，用户可在完成前调整；点击确认后才写入实际记录。页面刷新后恢复原进度。
6. **结束训练**：用户选择“轻松 / 刚刚好 / 偏吃力”，可补充一句不适。未完成计划时再选择下次“继续这一天”或“推进到下一天”。不生成长篇总结。
7. **复盘**：历史明确展示完整、部分或没有已确认组的记录。周完成次数只统计完整训练；实际组数和训练时长基于已保存记录，不把未确认的计划组计为实际数据。

## 4. 页面与功能范围

### 4.1 首页与训练体系

首页展示下一训练日、训练方向、每周完成情况和上次已保存训练。训练体系页说明连续 PPL 顺序、当前阶段和下一次建议，移除让用户挑选 A/B、器械或训练模板的必要步骤。

### 4.2 训练准备与计划预览

训练准备仅包含时间（30/45/60/90 分钟）、疲劳程度和疼痛/不适自由描述。计划预览显示动作、计划组数/次数/重量/休息、主动作连续性和简短调整原因。允许单动作替换和数字编辑。用户确认前计划为预览状态，不作为训练记录。

### 4.3 训练执行与记录

训练执行保留必要热身、正式训练、拉伸、组间计时和结束入口。每组记录实际重量、次数和确认时间；跳过、未开始、部分完成、完整完成的动作状态分开保存。跳过动作、提前结束和刷新恢复不得虚构已完成组。

### 4.4 数据与个人档案

数据页保留按日期排列的训练历史、实际组数、训练时长、周完成次数和动作反馈；不以跨器械可比性较弱的总训练容量作为主要指标。体重/体脂为选填，用户修改测量值时才产生身体测量点，训练启动不会自动伪造测量数据。

个人档案可编辑训练方向、频率、经验、长期限制和自由文本备注；可选启用 AI、在本机设置 API Key、管理暂停推荐动作，并导出/恢复本地备份。当前自由文本备注可供 AI 参考，但不会自动解析成结构化字段。

## 5. 训练计划规则

### 5.1 连续 PPL 与部分训练

训练日按推、拉、腿持续循环。完整完成后自动进入下一训练日；部分训练结束时由用户决定保持当天还是推进。该选择只影响下一训练方向，不会把部分记录标记为完整训练。旧分化计划在无进行中训练时映射为 PPL，同时保留历史和进行中训练。

### 5.2 动作数量与结构

- 30 分钟计划默认 6 个动作；45、60、90 分钟计划默认 8 个动作。
- 正式训练最多 8 个动作，结构优先覆盖当日 PPL 主要动作模式和肌群。
- 推日覆盖水平推、垂直推和肘伸；拉日覆盖垂直拉、水平拉、后束/上背和肘屈；腿日覆盖膝主导、髋主导、小腿和核心等必要模式。
- 主动作优先连续，便于比较真实表现；辅助动作在精选动作目录内变化，优先满足结构、近期使用和用户暂停要求。
- 有些疲劳时减少动作组数；比较疲劳时进一步降低重量。时间较短时减少动作数量，而不是只压缩显示内容。

### 5.3 历史表现与进阶

计划可读取同类训练的实际重量、次数、已确认组、动作反馈及整体训练感受。未确认目标、跳过动作和计划值不得作为完成表现。表现用于建议维持、小幅加重/减重、减少辅助训练量或避开有不适的动作；建议保持克制，用户可以在预览中调整并确认。

### 5.4 安全边界

AI 或本地规则不得诊断伤病。已知限制和当天不适需保守避开相关动作。训练数字必须经过范围和结构校验；重量不得出现非有限值，实际次数至少为 1。遇到明显疼痛或异常症状时停止相关动作并寻求适当专业帮助。

## 6. 可选 AI 计划适配

### 6.1 启用方式与职责

AI 默认关闭。用户在个人页明确启用并配置 DeepSeek API Key 后，生成计划时可以选择性地让 AI 根据当天情况、档案、近期实际训练和用户的自然语言请求适配本地规则计划。用户未启用或没有 Key 时直接使用本地计划。

AI 只可在本地提供的候选动作和计划范围内做适配，不改变动作位数量，不增加计划组数，不大幅改变次数、重量或休息，不得违反不适限制和 PPL 结构。训练开始后不再请求 AI。

### 6.2 隐私与失败回退

- Key 仅保存在当前浏览器，不进入代码和普通备份。
- 用户启用 AI 时，训练方向、经验、限制、备注、当天回答、近期最多四次同类训练实际记录和计划骨架会发给 DeepSeek；姓名不发送。
- 网络失败、超时、AI 返回格式错误或建议未通过校验时，保留本地计划和用户输入，简短说明已回退。
- 只有用户确认后的计划目标才进入训练；只有实际确认组才进入训练记录。

## 7. 训练记录与统计口径

### 7.1 每次计划和实际数据

计划值保存动作、目标组数、目标次数、目标重量和休息时间；训练历史保存训练日期、开始日期、完成时间、实际时长、整体感受、不适补充、PPL 推进选择，以及每个动作的目标和状态。每个实际组保存确认后的重量、次数和确认时间。

动作状态至少区分 `completed`、`partial`、`skipped`、`not_started`。未确认的组不写入实际组数组。修改预览计划不会改写旧训练记录。

### 7.2 统计

- **完成训练次数、完成率、连续训练天数、训练阶段完成次数**：仅完整完成的训练计入。
- **实际组数**：统计所有已保存训练中逐组确认的组，包括部分训练里的已完成组；跳过和未开始动作贡献为零。
- **实际时长**：按已保存训练的实际计时汇总，界面按分钟显示。
- **趋势判断**：使用实际重量/次数/组数、动作反馈和整体感受；计划值只用作目标比较，不能当作已完成数据。
- **体重与体脂**：只有用户填写或修改时记录，不从个人档案或训练活动自动造点。

## 8. 档案、存储与兼容

### 8.1 训练档案

档案包括训练方向、每周训练频率、经验、限制、自由文本备注、首次问卷状态和 AI 开关。新用户可逐题填写或跳过；问答草稿保存于本地。已有旧档案默认视为已完成问卷，避免重复打扰。结构化档案可在个人页编辑；自由文本备注会随 AI 请求发送，仅在 AI 开启时发生。

**待实现边界**：用户可以用自由文本补充训练备注；将自然语言自动解析为训练方向、频率或限制并确认更新，当前版本尚未实现。

### 8.2 本地存储与备份

训练数据保存在当前浏览器 `localStorage`，没有 IronTrack 自有后端。普通备份格式为 V3，导入兼容 V1、V2、V3；备份包括档案、计划、历史、身体数据、进行中训练和必要恢复信息，不包括 API Key。兼容升级须保留旧历史、进行中训练和可恢复快照，不静默截断或覆盖历史。

### 8.3 失败保护

计划、档案和训练结束提交应采用可检查的本地事务。写入失败时提示用户，保留进行中或待保存状态，支持重试或导出恢复数据。导入在写入前校验；失败时回滚本次导入并保留导入前快照。浏览器存储被用户或系统清理仍可能造成数据丢失，产品必须提示定期导出备份。

## 9. 异常与边界

- 无 AI、无网络、请求超时或返回不合规：使用本地规则计划，不阻断训练。
- 空值、非法数字、`NaN`、负值或超范围：不进入计划或历史；提示并保留可修正状态。
- 刷新、关闭页面或跨日重新进入：恢复进行中计划、当前动作和已确认组；不能重复生成训练记录。
- 部分训练保存失败：待保存检查点继续保留，用户可重试；周期状态只在本次事务成功后更新。
- 旧数据或旧备份迁移失败：保留原文或兼容快照，禁止用默认数据覆盖唯一副本。
- 导入错误：保持当前数据不变，并显示恢复结果。

## 10. 移动端、PWA 与发布

### 10.1 移动端要求

手机浏览器优先，关键按钮触控区域至少 44px，内容不横向溢出，输入键盘不遮挡当前输入和主要操作，布局处理刘海与底部安全区。根目录 `index.html` 是唯一发布入口；CSS、脚本、图标、动作目录和主图均使用项目本地资源。

V1.3 已修复 GitHub Pages 子路径下主图、图标和 Web App 清单路径；`manifest.json` 的入口和作用域定位到项目根路径。实际 iPhone Safari 添加到主屏幕、锁屏返回与文件导入导出仍需实机验收，桌面浏览器检查不替代实机验收。

### 10.2 部署与缓存

GitHub Pages 由推送 `main` 的 Actions 工作流发布。Service Worker 对页面和动作数据使用网络优先、应用壳资源使用缓存优先；每次发布资源前必须递增 `CACHE_VERSION`，确保旧缓存更新。发布后核验 Actions 成功、线上入口和关键脚本/图片/图标/清单可访问。必要时可以回滚到上一提交；回滚版本也要使用新的缓存版本号，避免客户端继续使用错误缓存。

## 11. V1.3 验收标准与证据

### 11.1 已验证

- 新用户按题填写或跳过；旧用户不重复问卷；档案草稿可恢复。
- 当天只显示时间、疲劳和不适三项；不显示训练场地和器械配置选择。
- PPL 30 分钟生成 6 个动作，45/60/90 分钟生成 8 个；完整计划维持结构平衡。
- 可选 AI 受限于合格候选和数值范围；自动回归覆盖脱敏上下文、合法建议应用和异常回退。
- 每组必须由用户确认后进入实际数据；目标值和实际值分开保存。
- 部分训练须选择是否推进；部分训练不增加完成次数、完成率、连续训练天数或训练阶段次数；已确认组计入实际组数。
- 写入失败、刷新恢复、跨日恢复、旧备份导入、坏备份拒绝和历史保留通过数据回归。
- `npm run build`、`git diff --check`、19 组数据可靠性回归通过；GitHub Pages 工作流成功，线上页面、脚本、主图、图标、清单和 Service Worker 均可访问。
- 浏览器中已走通新用户问卷、当天三问、短时计划、逐组确认和部分训练保存闭环。

### 11.2 待验证或尚未实现

- **待实机验收**：iPhone Safari 添加到主屏幕后的图标、独立运行、锁屏恢复、虚拟键盘与真实触控；iPhone 上备份下载和恢复。
- **待实现**：自然语言更新结构化训练档案字段，并在写入前简短复述供用户确认。
- **不作为当前门槛**：多设备云同步、总训练容量、动作百科、训练长总结和自动医疗/康复建议。

## 12. 分阶段实施与后续取舍

### 阶段一：数据与恢复保护（已发布）

目标是保证用户原有资料、历史和进行中训练在迁移、保存失败、刷新和备份恢复时可找回。范围包括事务写入、异常恢复、V1/V2/V3 备份兼容、待保存训练检查点和不截断历史。风险是旧数据形状不一致；通过脚本故障注入、迁移回归、旧备份恢复和导入回滚验证。

### 阶段二：PPL 与训练流程收敛（已发布）

目标是以持续数周的方向和真实记录维持训练连续性，减少训练前选择并让短时计划更可用。范围包括新档案、当日三问、PPL 自动推荐、6/8 动作数量、计划预览、逐组实际记录、简短结束反馈和部分训练推进选择。风险是旧计划和旧状态兼容；通过动作引擎、状态机、训练闭环浏览器验证和统计口径回归验证。

### 阶段三：可选 AI 适配与线上发布（已发布）

目标是让已有 AI 用户能自然语言调整当天计划，同时保持无 AI 时流程完整。AI 仅在用户启用后读取最少必要档案和真实记录，并经过本地边界校验；失败回退本地计划。发布流程包括 Service Worker 缓存更新、Pages 子路径资源核验和线上工作流确认。用户数据未通过未授权路径外发。

### 后续小步迭代

## 历史需求（已被 V1.3 取代）：V1.1 UI 视觉改版

### 14.1 改版目标

在不改变训练逻辑、数据结构和历史数据的前提下，重新建立 IronTrack 的视觉系统和页面层级，使其更接近高级运动品牌的个人训练产品，同时保持训练现场的清晰、高效和单手可操作性。

本轮允许重新排版、调整按钮位置和减少不必要的卡片容器。按 2026-09-01 确认变更，删除“我的 → 知识库”占位入口及内容；除此之外不得删减现有功能入口，不得改变 PPL、动作轮换、AI 生成、训练记录、反馈、备份与恢复规则。

### 14.2 视觉方向

- 采用“午夜竞技”风格：近黑背景、暖白文字和荧光绿品牌主色。
- 只提供深色模式，本轮不增加浅色主题或主题切换。
- 荧光绿用于主要按钮、当前状态、进度和关键数字；警告、错误和成功状态可以使用独立语义色，但不得形成第二套品牌主色。
- 品牌名使用粗体大写；页面标题和关键训练数字强调力量感，普通说明文字保持简短清楚。
- 减少“所有内容都放入卡片”的表现，优先使用留白、字号、对齐和分隔线建立层级。
- 页面文案采用简短、有力量的语气，只在首页、训练开始和训练完成等关键时刻使用。

### 14.3 图片与品牌表达

- 登录页和今日首页使用低光环境中的真实训练人物照片，动作清楚但不突出面部。
- 计划、正式训练、数据和设置页面不使用大面积照片，以免影响阅读和操作。
- 正式资源必须随项目本地发布，不依赖运行时外部图片链接；图片中不得包含第三方品牌、文字或界面元素。
- 首页采用“品牌与效率平衡”布局：照片约占半屏，主训练入口清楚，首屏同时保留本周进度、连续训练和上次训练摘要。

### 14.4 页面布局

- 登录页：全屏训练人物背景；品牌、已有用户名和新用户名输入位于安全区域内。
- 今日首页：突出推荐训练日、简短口号和“生成今日计划”，同时展示本周状态和上次训练。
- 训练体系页：以 PPL 周期时间线为主，分层展示核心动作、A/B 方案和训练阶段。
- 生成前设置页：快捷选项分组，必填状态、不适提示和选中状态清楚区分。
- 计划预览页：核心动作优先，辅助动作使用简洁列表；保留锁定、替换及数字编辑。
- 训练执行页：采用“单组专注”布局，突出当前动作、重量、次数和完成按钮。
- 数据页：优先展示本周统计、核心动作趋势和按时间排列的训练历史。
- 我的页面：身体资料、器械、API 和本地备份分区展示，保持工具化表达。
- 底部导航保留中央训练按钮，其他四个入口降低视觉权重。

### 14.5 训练页与底部安全区

现有版本在 390×844 视口、页面位于顶部时，“完成本组”按钮与固定底部导航存在约 40px 重叠，用户需要下滑才能完成操作。V1.1 必须修复该问题。

- “完成本组”等训练主操作固定在底部导航上方，无需下滑即可操作。
- 页面底部留白统一按“导航栏高度 + 系统安全区 + 额外间距”计算。
- 次要操作降低视觉权重，必要时收纳到“更多操作”，但功能不得删除。
- 虚拟键盘打开时，当前输入框必须保持可见；固定操作区不得遮挡输入框。
- 重量和次数继续支持直接输入，左右调整按钮继续保留，并沿用现有调整规则。

### 14.6 响应式与可访问性

- 动作名称和关键数字在完整显示的前提下尽量放大。
- 长动作名称最多两行；文字和数字不得裁切、重叠、异常换行或被底栏遮挡。
- 可点击区域不小于 44px，保证训练时单手操作。
- 页面不得产生横向溢出。
- 至少验收 320×568、375×667 和 390×844 三种视口。
- 页面应正确处理手机刘海、底部手势区域和虚拟键盘。

### 14.7 动效

- 首页照片、标题和数据模块采用较明显的分层进入动画。
- 页面切换、进度和数字变化具有统一的运动节奏。
- 重量、次数、计时和主要训练按钮必须即时响应，不得为动画等待。
- 系统启用“减少动态效果”时，自动移除大幅移动和连续动画，只保留必要状态反馈。

### 14.8 数据与兼容边界

- 继续使用现有本地存储键和数据结构，UI 改版不引入数据迁移。
- 发布不得清除个人资料、训练历史、周期状态、今日计划或进行中的训练。
- API Key继续由用户自行填写，不写入代码，也不进入普通备份。
- 现有训练计划生成、动作替换、反馈、数据导入导出及刷新恢复能力必须完成回归测试。

### 14.9 UI 改版验收

1. 登录、首页、训练体系、训练设置、计划预览、训练执行、数据和我的页面使用同一套视觉系统。
2. 首页首屏具有明确品牌视觉，同时能看到主要训练入口和关键训练状态。
3. 训练执行页的动作名称、重量、次数和完成按钮在目标视口中完整显示。
4. 固定底栏不覆盖主按钮、次要操作或正文；“完成本组”无需下滑即可点击。
5. 虚拟键盘打开后，正在编辑的重量或次数输入框保持可见。
6. 动画明显但不延迟训练操作；减少动态效果设置生效。
7. 原有本地数据、AI 计划、本地备用计划、训练恢复、动作反馈和备份恢复均正常。
8. 线上资源不依赖外部图片地址，静态检查、窄屏验收和主要训练闭环全部通过后方可发布。

详细页面和实施规格见 `docs/superpowers/specs/2026-08-31-irontrack-ui-redesign-design.md`。

- 页面必须显式声明 iPhone 主屏幕图标，并使用有效的 Web App 清单；图标资源随项目本地发布，不依赖外部地址。

- 主屏幕名称为 `IronTrack`，从主屏幕打开后保持独立 Web App 显示方式，主题色与现有近黑界面一致。

## 历史需求（已被 V1.3 取代）：V1.2 规则主导训练计划重构

### 16.1 变更目标

V1.2 将训练计划生成从“规则生成骨架、AI 做适配”调整为“本地规则直接生成完整计划、AI 只做解释和评价”。本次变更的目标是降低 API 返回不稳定对训练闭环的影响，减少专业但低频的冗余功能，让用户打开网页后更稳定地得到当天可执行训练安排。

该章记录 V1.2 当时的重构需求和实施方案。自 V1.3 起，AI 已作为可选计划适配重新进入计划生成流程；以本文第 1～12 章为当前需求。

### 16.2 产品边界

- IronTrack 继续面向产品所有者本人：有一定力量训练经验，采用 PPL 分化，主要在健身房训练。
- 基础训练计划由固定 PPL 模板、本地动作白名单、历史记录和当天状态计算生成。
- AI 不参与基础计划生成，不作为动作选择、训练量、周期推进或合理性判断的前置条件。
- AI 只在用户需要时用于解释计划、查看动作示范说明、训练后评价和后续指导。
- 用户保留手动调整权限，可以根据器械占用、身体状态和个人偏好替换动作或修改组数、次数、重量和休息时间。

### 16.3 PPL 单次训练结构

每次训练默认约 8 个正式训练动作，目标训练时长为 45～60 分钟。系统通过组数、重量、次数和休息时间控制训练量，不以增加大量动作作为常规方案。

Push 日默认结构：

- 胸部 3 个。
- 肩部 2 个。
- 三头 2 个。
- 机动 1 个。

Pull 日默认结构：

- 背部垂直拉 2 个。
- 背部水平拉 2 个。
- 后束 / 上背 1 个。
- 二头 2 个。
- 机动 1 个。

Leg 日默认结构：

- 股四头主导 2 个。
- 髋主导 / 臀腿后侧 2 个。
- 单侧稳定 1 个。
- 小腿 1 个。
- 核心 1 个。
- 机动 1 个。

机动位用于补弱项、处理器械占用、替换不适动作或根据当天状态降低强度。机动位不得破坏当日主要结构。

### 16.4 动作白名单

项目可以保留已引入的开源动作库作为数据来源和后台资料，但自动训练计划只从固化后的 PPL 动作白名单中选择。

白名单规模暂定为每个 PPL 训练日约 20 个候选动作，总规模约 60 个动作。当天实际训练仍只安排约 8 个动作。

白名单筛选原则：

- 优先选择健身房常见器械能完成的动作。
- 优先选择名称直观、动作路径清楚、容易学习的动作。
- 优先选择适合有一定基础的初级训练者长期执行的动作。
- 暂不自动推荐技术门槛高、风险不好判断、动作名称花哨或过度细分的动作。
- 白名单外动作可以作为资料保留，但不进入自动训练计划。

白名单不再拆分“常用推荐”和“可选变式”等复杂等级。后续开发只需维护一份可进入自动计划的合格动作池。

### 16.5 周期与轮换规则

- Push、Pull、Leg 三次训练构成一个 PPL 小周期。
- 3 个 PPL 小周期构成一个动作稳定期，即约 9 次训练后再评估主动作轮换。
- 主动作在稳定期内保持稳定，便于比较重量、次数、完成度和身体反馈。
- 辅助动作可以变化更快，用于覆盖肌群、适配器械和增加训练趣味性。
- 系统优先保证主动作质量和周期稳定；如果训练时长、疲劳感或完成度异常，优先减少辅助动作或降低辅助训练量，而不是频繁改动主动作。
- 连续未完成目标、明确不适、器械不可用或用户主动调整时，才允许提前触发主动作替换建议。

### 16.6 AI 介入场景

AI 入口从“生成基础计划”调整为以下轻量辅助场景：

- 计划解释：说明当天为什么练这个训练日、为什么采用当前动作结构和训练量。
- 动作示范：提供动作要点、发力提示、常见错误和保守注意事项。
- 训练评价：基于已完成记录、动作反馈、训练时长、完成率和本地计算结果评价本次训练。
- 后续指导：在规则结果基础上解释下次维持、加重、减量、减少辅助动作或替换动作的原因。
- 异常建议：在用户反馈疲劳、不适或连续完成不好时，给出保守建议，但不得进行诊断或治疗承诺。

AI 输出只能作为解释和建议展示。任何会影响训练计划的动作、组数、次数、重量或休息时间变化，都必须先通过本地规则校验，并由用户确认。

### 16.7 前端影响

- 计划生成入口不再以 API Key、网络或 AI 成功为前提。
- 生成前设置页继续收集训练日、状态、可用时间、训练环境、不适部位和避开动作，但提交后优先进入本地规则生成。
- 计划预览页应显示规则来源、PPL 结构分配、主动作稳定原因、辅助动作选择原因和手动替换入口。
- AI 相关入口应调整为“解释”“动作要点”“训练评价”“后续建议”等语义，不再表达为基础计划生成能力。
- 无 API Key 或 AI 失败时，不显示阻断式错误；仅在用户点击 AI 辅助内容时提示该解释或评价暂不可用。
- 页面应继续保持训练现场优先：当天怎么练、当前动作、重量、次数和完成按钮优先级高于长文本说明。

### 16.8 数据与规则影响

- 需要维护本地 PPL 白名单动作池、动作结构槽位、主动作稳定期状态、辅助动作轮换记录和用户手动调整记录。
- 现有 `localStorage` 中的个人档案、计划、历史、进行中训练、动作反馈、周期状态和 API Key 必须继续兼容。
- 旧历史中的动作名称和统计记录不得因白名单缩减而丢失；无法匹配白名单的旧动作保留历史展示，但不进入新的自动计划。
- 备份导出应包含白名单版本、主动作稳定期、周期状态、历史记录、动作反馈和用户调整记录；继续排除 API Key。
- 训练记录和基础复盘不得依赖 AI 返回。训练完成后，系统先保存结构化记录并计算基础结论，再允许 AI 基于结论生成评价文字。

### 16.9 开发实施建议

为降低改动风险，本次重构建议按以下顺序实施：

1. 先抽出本地计划生成规则，保证无 API 时能直接生成符合 PPL 结构的约 8 个动作计划。
2. 固化 PPL 白名单和三类训练日槽位，不再让自动计划读取完整开源动作库。
3. 调整计划预览和训练体系页文案，使用户看到的是规则计划、结构原因和手动替换入口。
4. 将 AI 调用从计划生成链路中移出，改为解释、动作要点、训练评价和后续建议的按需入口。
5. 补齐旧数据兼容和备份字段，确保已有训练记录、进行中训练和周期状态不被清空。
6. 回归测试计划生成、动作替换、训练执行、刷新恢复、训练完成、数据复盘、备份导入导出和无 API 场景。

### 16.10 验收标准

1. 未设置 API Key、网络失败或 AI 请求失败时，用户仍能生成当天 PPL 计划，并完成训练记录。
2. Push、Pull、Leg 计划默认约 8 个动作，结构分别符合第 16.3 节的分配。
3. 自动计划只从 PPL 白名单动作池中选择动作；白名单外动作不进入新计划。
4. 每个 PPL 训练日约 20 个候选动作，总白名单约 60 个动作。
5. 主动作在约 9 次训练的稳定期内保持，不因追求变化而频繁替换。
6. 辅助动作可以轮换，但不得破坏当日 PPL 结构，也不得堆叠重复刺激。
7. 疲劳、训练超时或完成度异常时，系统优先减少辅助训练量或降低辅助动作强度。
8. 用户可以手动替换动作和修改训练数字，替换优先限定在同训练日、同肌群或相近训练目的的白名单动作中。
9. 训练开始后不调用 AI；刷新或临时退出后可以恢复当前动作、当前组和已完成记录。
10. 训练完成后先保存结构化记录和本地统计，再按需调用 AI 生成评价或指导。
11. AI 入口只用于解释、示范、评价和指导，不再作为基础计划生成按钮或必要流程。
12. 旧历史、个人档案、当前周期、进行中训练和普通备份恢复均保持可用。
